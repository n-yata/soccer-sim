# 設計

## スパイクの結果（2026-10-24。CPU 同士 100試合・シード 20261024。一時的な切り替えで比べ、作業の後に戻した）

| 案 | プレー中の入れ替わり | 点数 | 保持の平均 | 守備がぴったり読んだ割合 |
|---|---|---|---|---|
| いま（forward 1.0・shot 0.75） | 2.3 | 2.94 | 3.8 | 9% |
| 同数で背後にカバーがいればロスト | 2.6 | 3.03 | 3.6 | 8% |
| 読まれていない同数はすべて膠着 | 2.3 | 1.14 | 5.2 | 8% |
| 隣の読みの同数はロスト（規則だけ） | 2.8 | 2.67 | 3.7 | 8% |
| CPU の先読み 2.0（攻撃の加点はそのまま） | 4.8 | 1.89 | 3.2 | 21% |
| CPU の先読みだけ（3.0・forward 1.75・shot 1.0） | 5.7 | 2.71 | 2.6 | 24% |
| **先読み 2.0＋隣の読み＋forward 1.5・shot 1.25** | **6.8** | **2.24** | **2.5** | 23% |
| 先読み 2.0＋隣の読み＋forward 1.5・shot 1.5 | 6.9 | 2.49 | 2.4 | 23% |
| 先読み 2.0＋隣でも +2＋forward 1.5・shot 1.25 | 7.3 | 2.13 | 2.4 | 21% |

- 先読みだけでは、守備がぴったり読む割合が 24% 前後で頭打ちになり、入れ替わりは 6回に届かない。
- シャビと相談し（2026-10-24）、「先読み＋隣の読み（同数は奪える）」に決めた。

## 判定（アルゴリズム5）

- `GameEnums.ReadKind { NONE, NEAR, EXACT }` を足す。
- `JudgeDetail.is_read: bool` を `read: ReadKind` に置き換える。意味が「当たったか」から「どれだけ近いか」に変わるため、改名する（coding-common「意味論が変わったら改名」）。
  - `RevealView.is_read` も `read` にする。呼び出し側はすべて grep で洗い出す。
- `OpenPlayJudge.read_of(restricted, compare, ball) -> ReadKind`（ball は実装中に追加。下記）:
  - 同じエリアなら EXACT。
  - 制限したエリアがボールのエリアなら NONE（実装中に追加。下記）。
  - 同じゾーンでレーン差が1なら NEAR。
  - それ以外は NONE。
- **ボールのエリアへの寄せは隣の読みに数えない**（2026-10-24。実装中に判断）。
  - 数えると、ボールへのプレスだけで、横への同数のパスがすべて奪われる。判定例 JE-02（マンツーマンでカバーのいない外側へ通す）が、JE-03（読んで奪う）と同じ結果になって成り立たない。
  - 持っている選手への寄せは、運ぶ先を読んだのではない。
  - 計測（3シード × 50試合、anticipation 2.0・forward 1.5・shot 1.25）: 数える 6.9回・2.16点、数えない 6.8回・2.25点。入れ替わりはほぼ変わらない。
- `outcome_of`:
  - シュート: 今と同じ。EXACT の同数だけ SAVE（NEAR はシュートに効かない）。
  - シュート以外:

    | 読み | 結果 |
    |---|---|
    | EXACT | diff ≥ 2 で ADVANCE、それ以外は LOSS |
    | NEAR | diff ≥ 1 で ADVANCE、それ以外は LOSS |
    | NONE | 今と同じ |

  - 要る人数差は、読みの段階ごとの定数の表で持つ（規則の定義。調整値ではない。前の作業の実装レビューで、定数でよいと確認済み）。
- トランジションは、今と同じく NONE。

## CPU（アルゴリズム8）

- `CpuConfig.anticipation_bonus`（0 以上）を足す。
- `CpuPlanner.goal_bonus` を次のようにする。
  - 守備の手で運ぶ先（制限するエリア）があれば、`anticipation_bonus × (target.zone − ball.zone)`。
  - 守備の手の制限するエリアは、攻撃側の視点の座標（`OpenPlayJudge` が `defense.target` と攻撃側の視点の比較エリアを直接比べている）。ボールも保持側の視点なので、そのまま引ける。
  - 名前は、守備の加点を含むので `goal_bonus` から `situation_bonus` に変える。
- `ConfigRepository`: `anticipation_bonus` も `_is_bonus_valid` で検査する。
- 初期値: スパイクの最有力（anticipation 2.0・forward 1.5・shot 1.25）を起点に、計測のテストで複数シードの平均を見て決める。
  - **決めた値: anticipation 2.0・forward 1.5・shot 1.5**（3シード × 50試合: 約2.41点・入れ替わり 約7.0回・保持の平均 約2.4ターン・利用者を模した手 約1.65点）。shot 1.25 では約2.25点・6.8回で、点数の目標の中央（2.5点）に近い 1.5 にした。
  - 実装レビューで10シードを測り、どのシードでも目標の範囲に入った（入れ替わり 6.6〜7.5回・2.12〜2.70点）。

## 表示

- `JudgeReasonFormatter._cause`:
  - LOSS／SAVE で読みが EXACT: 「読まれて」／「読み切って」（今と同じ）。
  - LOSS で読みが NEAR: 「隣を読まれて」／「隣を読んで」。
- 判定の内訳（`detail`）は変えない。

## 計測

- `MatchBalanceProbe.run` が、シードの配列を受け取り、各シードで試合を回して合計する。
- `match_balance_test`:
  - 3シード × 50試合 = 150試合。CPU 同士の計測は1回だけ回し、テストで共有する。
  - 確かめること:
    - プレー中の入れ替わり（`turnovers_per_match`）が 6〜10回。
    - 点数が 2〜3点。
    - 保持の平均が 2〜4ターン。
    - 利用者を模した手の得点が 1.0〜2.5点。
    - 読んだとき（EXACT・NEAR）に奪う割合が、外したとき（NONE）より高い。
  - 保持の回数（キックオフを含む）の 6〜10回の検査はやめる（目標はプレー中の入れ替わりで測るため）。
