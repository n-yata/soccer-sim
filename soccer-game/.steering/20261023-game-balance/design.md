# 設計

## 計測で決めたこと（2026-10-23〜24）

一時的な切り替え（スパイク。作業の後に戻した）で、規則の候補を CPU 同士の試合（150試合・固定シード）で比べた。

| 案 | 1試合の点数 | 1試合の入れ替わり | 読みを当てたときに奪う割合 |
|---|---|---|---|
| いま | 0.31 | 2.8回 | 6% |
| 読みを当てた同数・+1 で奪う | 0.31 | 4.3回 | 42% |
| ＋CPU がゴールを狙う | 1.27 | 5.4回 | 85% |
| ＋敵陣の同数を GK のカバーで止めない＋シュートは同数でも読まれていなければ決まる | 約 3.0（重み 1.0／1.0） | 6.4回 | 46% |
| （参考）同数はすべて奪う | 0.24 | 7.8回 | 外しても 36% 奪える。読み合いが効かない |

- 要求の2つの直し方（守備が奪いやすく・CPU がゴールを狙う）だけでは、1.3点で頭打ちになった。
  - 敵陣の同数を止める GK のカバーと、「人数で上回らないと決まらない」シュートが壁だった。
- そのため、シャビと相談した（2026-10-24）。シュートの条件と GK のカバーも変えることにした（要求のスコープ外から入れた）。
- GK のカバーとは、敵陣へ運んだときの同数を、GK が背後でカバーしている扱いにして膠着にする規則。大外は届かない扱いで、表示は「GK」「GK外」。
  - これをやめても GK そのものは消えない。ゴール前の守りは、シュートの規則（同数で読まれたら止める）が担う。

## ルール（アルゴリズム5の手順5〜6を置き換える）

「読みを当てた」＝守備が制限したエリアが、比較エリア（運ぶ先。シュートはボールのエリア）と同じ。

| 手 | 結果 |
|---|---|
| シュート | 攻撃側が人数で上回れば得点。同数で、読みを当てられていなければ得点。それ以外はシュート阻止 |
| シュート以外・読みを当てられた | 攻撃側が2人以上多ければ前進。それ以外（1人多い・同数・少ない）はロスト |
| シュート以外・読みを外された | 攻撃側が多ければ前進、少なければロスト。同数なら、背後に守備のカバーがいれば膠着、いなければ前進 |

- カバーは、守備のカバー（背後のエリアで守備側が攻撃側より多い）だけになる。
  - 背後が盤外（敵陣）なら、カバーなし。
  - `CoverKind` から `GOALKEEPER`・`OUT_OF_GK_REACH` を外す。いま使っているのは判定の内訳・ヒントの札・判定理由の文だけで、保存データにはまだ書いていない（保存の作業の前）。
- `JudgeDetail` に `is_read: bool`（読みを当てられたか）を足す。
  - 判定（`OpenPlayJudge.judge`）で決める。
  - トランジション（カウンター・即時奪回）と、ヒント（相手が何もしない場合）では偽。
  - `outcome_of(detail, is_shot)` は `detail.is_read` を読む。トランジションのカウンターも同じ関数で判定し、読みは偽のまま。
- 判定理由の文: 読みを当てられて奪われた・止められたときは、「読まれて」の句にする。
  - 例: 「中盤・中央で 1対0。読まれてロスト」「敵陣・中央で 1対1。読まれてシュート阻止」
  - `RevealView.is_read` を足し、`ViewConverter.reveal` で写す。
- ヒント（FR-19）の人数の計算は変えない。カバーの表示から「GK」「GK外」がなくなる。

## CPU の評価値（アルゴリズム8に足す）

- `CpuConfig` に、ゴールへの加点の重みを2つ足す（どちらも 0 以上の有限の値。範囲外は初期値に戻す）。
  - `forward_bonus`: 前へ運ぶ手の加点（1ゾーンあたり）。
  - `shot_bonus`: シュートの加点。
- `CpuPlanner.goal_bonus(hint, ball, cpu)`
  - 攻撃の手・奪取側の手で運ぶ先があれば、`forward_bonus × (運ぶ先のゾーン − ボールのゾーン)`。後ろへ運ぶ手は負。
  - シュートなら `shot_bonus`。
  - それ以外は 0。
  - 評価値は「人数差 ＋ 方式の癖の加点 ＋ ゴールへの加点」。
- 初期値は、計測で 2〜3点・6〜10回に入る値に決める（スパイクでは 1.0／1.0 で約 3.0点・6.4回）。
- **決めた初期値: forward_bonus = 1.0、shot_bonus = 0.75**（2026-10-24。MatchBalanceProbe・100試合）。

  | forward／shot | 点数（シード 20261024／7／99） | 入れ替わり | 保持の平均 | 利用者を模した手の HOME の得点 |
  |---|---|---|---|---|
  | 1.0／1.0 | 3.35 | 6.7 | 3.6 | 2.31 |
  | **1.0／0.75** | **2.94／2.52／2.58** | **6.3／6.1／6.1** | **3.8／3.9／4.0** | **2.09／1.66／1.82** |
  | 0.75／0.75 | 2.39 | 6.0 | 4.0 | 1.79 |
  | 1.0／0.5 | 2.27 | 5.8 | 4.2 | 1.70 |

  - 点数と入れ替わりは連動する（シュートの成功率が9割を超え、保持1回あたりの得点が約0.45）。入れ替わりを増やすと点数も3点を超える。
  - そのため入れ替わりは目標の下限（約6回・保持の平均 約4ターン）に留まる。これ以上増やすには、判定の規則をさらに変える必要がある。
  - 試した規則の追加案（どちらも戻した）:
    - 読まれたシュートも +2 が要る: CPU の守備がシュートを読むことが少なく、ほぼ変わらない（3.20点・6.7回）。
    - 読まれた手が前進するのに +3 が要る: 入れ替わりが +0.4回だけ。
  - **プレー中の入れ替わり**（ロスト・シュート阻止・奪回成功。実装レビュー H-3 で分けて数えた）は 1試合 約2.3回（読まれた手に +3 を要しても 2.7回）。上の「入れ替わり」（保持の回数）は、得点後のキックオフで渡った分を含む。
    - シャビと相談し（2026-10-24）、今回は保持の回数で測る形のまま区切り、プレー中の入れ替わりを増やすのは別の作業にした。計測の補助は turnovers も数えて summary に出す。
  - 利用者を模した手の目安は、当初の 0.7〜1.8点から **1.0〜2.5点** に改めた。CPU 同士で1チーム約1.4点なので、最善手を選びやすい手はそれより多く取れてよい。
- ヒント（利用者に見せる人数差）は変えない。

## 計測（テストとして残す）

- `tests/balance/match_balance_test.gd`（新規）。補助の `MatchBalanceProbe`（tests の中）を置く。
  - 固定シードで、CPU 同士の試合を回して、次を数える。
    - 1試合の点数。
    - 攻守の入れ替わり（保持の回数と長さ）。
    - シュートの数。
    - 読みを当てた／外したときに奪う割合。
  - 同梱の設定（`cpu_config.tres`・`match_rule_config.tres`）を使う。
- 確かめること:
  - CPU 同士: 点数の平均が 2〜3点。入れ替わりが 6〜10回。保持の平均が 2〜4ターン。
  - 利用者を模した手（CPU と同じ評価で、温度 0.2・下限 0 の手。最善手を選びやすい）を HOME にしたとき、HOME の得点が 1試合 1.0〜2.5点（計測の後に改めた。上の「決めた初期値」）。
  - 読みを当てたときに奪う割合が、外したときより高い。
- 試合数は 100（全体のテストの時間が約 25秒延びる見込み）。CPU 同士の計測は before() で1回だけ回し、2つのテストで共有する。
