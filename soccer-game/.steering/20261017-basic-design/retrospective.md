- 第2回: Critical 0 / High 1 / Medium 2 / Low 8。High（N1）は、Low の対応で入れたキャッシュが試合の終了で古くなる欠陥。修正した

- 全文と積み残し: [review-report.md](./review-report.md)

## 学び
- 設計文書でも、コミット前レビューは「静かに誤る」欠陥を多く拾う。特に、保存・削除・再開・終了処理の組み合わせ（どの時点で、どの状態のデータが残るか）は、ユースケースを1本ずつ描いただけでは見落とす。「同じ起動の中で次に何をするか」までたどる必要がある
- 小さな改善（読み込み結果のキャッシュ）が、別の経路（終了処理からの戦績の追加）と組み合わさって新しい High を生んだ。キャッシュを入れるときは、書き込みの経路をすべて洗い出す
- 「UI は座標を変換しない」と決めたなら、UI に渡るすべての値の視点を表にする。決めただけで、どの値がどの視点かを書かずにいると、UI での変換が前提として残る
- drawio MCP の道具はブラウザのエディタを操作するもので、ワイヤーフレームを最初から描くより、スクリプトで XML を生成してエディタに読み込み、画像に書き出して確かめるほうが確実だった。画像で見て、盤面の人数と判定理由の文の食い違いに気づけた
- 作業の途中で、worktree をやめて `main` で作業する決定があった。未コミットの変更はパッチにして `main` に移せた（`git apply --3way`）

## 改善提案
- kit の `specs-basic-design` のガイドに、「保存・削除・再開がある場合は、状態（どのデータが残るか）の遷移を1枚の表にしてから各ユースケースを描く」という手順を足すとよい
- ワイヤーフレームの生成スクリプトはスクラッチに置いて使い捨てにした。画面が増えて手直しが増えるようなら、`tools/` に置いてリポジトリで管理するかを検討する
