#### Medium（対応推奨）

**M-1 [運用/バグ] `.mcp.json` の相対パス `tools/mcp/drawio-mcp.mjs` が CWD 依存**
- `node tools/mcp/drawio-mcp.mjs` は MCP サーバー起動時のカレントディレクトリ基準で解決される。Claude Code をリポジトリのルート以外（例: `godot/` 配下）で起動したセッションでは `Cannot find module` で drawio だけ静かに接続失敗し、`/mcp` に CONNECTION_CLOSED が出るだけで原因が分かりにくい。
- 修正案: ドキュメントに「drawio MCP はリポジトリルートで起動したセッションでのみ有効」と明記する。またはルート以外での起動もサポートしたいなら、`.mcp.json` の環境変数展開でルートを渡す（Claude Code が MCP の args 中の `${CLAUDE_PROJECT_DIR}` を展開するかは未検証）。

**M-2 [セキュリティ (A05/A01 系, CWE-377)] 共有一時ディレクトリへの予測可能なパス・既定パーミッションでの書き込み**
- `join(tmpdir(), "drawio-mcp")` を `mkdirSync(recursive)` で作り、所有者検証なし。ファイル名 `<cwd名>-<pid>.json` は予測可能で、`writeFileSync` は既存シンボリックリンクを辿る。Linux/macOS の共有 `/tmp` では、別ユーザーが先に `drawio-mcp/` を作っておけばファイル差し替え・シンボリックリンク経由の上書きが可能。ファイル自体も既定 0644 相当で作られ、`cwd` の絶対パス（ユーザー名を含む）とポート番号が他ユーザーから読める。
- 影響範囲: Windows（`tmpdir()` はユーザーごと）・単一ユーザーの Dev Container では実害は小さい。条件が揃った場合（マルチユーザーの Linux ホスト）に限られるため Medium とした。
- 修正例: `mkdirSync(infoDir, { recursive: true, mode: 0o700 })` の後に `lstatSync` で所有者を検証し、`writeFileSync(infoFile, json, { flag: "wx", mode: 0o600 })` で既存ファイル・リンクを辿らない。`cwd` の絶対パスが不要なら書き出さないのも手。

#### Low / 改善提案

- **L-1 [運用] URL ファイル書き出し失敗の完全な握りつぶし**: 起動を続ける判断は妥当だが、失敗時は `editorUrl` が見つからず原因も分からない。stderr に1行出すとよい（stdout は MCP の通信路なので使わない）。
- **L-2 [バグ] ポート予約から子プロセスの bind までの TOCTOU**: 確率は低く、取られた場合はサーバーが「already in use」で終了しラッパーも同じ終了コードで落ちるため可視化される。`/mcp` で再接続すれば直る旨はドキュメント済み。
- **L-3 [運用] 強制終了時に URL ファイルが残る**: TerminateProcess / SIGKILL では `exit` ハンドラが走らず、古い `drawio-mcp/*.json` が残る。起動時に死んだ pid のファイルを掃除するか、ドキュメントに「pid が生きているもののみ有効」と書き添える。
- **L-4 [運用] Windows の `shell: true` ＋ 引数配列**: 引数は固定値と OS 割り当てのポート番号のみでコマンドインジェクションの余地はない（確認済み）。Node 24 以降では DEP0190 警告が stderr に出る（使用する Node の版は未検証）。また `child.kill()` は cmd.exe しか落とさないが、孫の node は stdin が閉じれば自ら shutdown する（2.3.0 の実装にあると報告されており、再検証はしていない）。
- **L-5 [セキュリティ/参考・差分外のライブラリ仕様]**: drawio-mcp-server の HTTP 側は CORS が `origin: "*"`。今回の変更で 127.0.0.1 限定かつ毎回ランダムなポートになり、既定構成より攻撃面は縮小した。改善方向の変更であり対応不要。
- **L-6 [運用] 推移的依存は固定されていない**: `drawio-mcp-server@2.3.0` 本体は固定されたが、npx の解決ではロックファイルが効かず、推移的依存は起動ごとに変わりうる。従来（版を固定しない）より改善しており、申し送りで足りる。

#### 問題なし
- シークレット・認証情報の直書き: なし。ラッパー内の URL はローカルの `127.0.0.1` と OS 割り当てのポートのみで、外部エンドポイントを含まない。ドキュメントにも実 URL・キーなし
- インジェクション: npx への引数は定数と数値のみで、外部入力が流れ込む経路なし
- `--host 127.0.0.1` が HTTP サーバー（`serve` の `hostname`）と WebSocket サーバー（`WebSocketServer` の `host`）の両方に効くことを、2.3.0 の実装で確認
- エディタが動的なポートに接続できること: WebSocket のポートは `/api/config` が `websocketPort: config.extensionPort` で返し、固定の 3333 に依存しない。`editorUrl` の `127.0.0.1` は、プラグインが `window.location.hostname` を使う実装と整合
- ポートの重複: 2つのサーバーを同時に開いてから受け取るので、同じ番号にならない
- 終了コード: 子プロセスの終了コードを引き継ぎ、失敗が呼び出し元に伝わる
- 起動失敗時: `error` ハンドラが stderr に理由を出し、終了コード 1 で終わる
- 切り戻し: `.mcp.json` を戻すだけで revert 可能
- ドキュメント: 理由・URL の取得方法・障害時の手順が `repository-structure.md` に反映済み。構成図と `tools/` の配置ファイル一覧も更新済み
- 性能: 起動時1回の軽量処理のみ

### 対応

### Low / 改善提案
- **L-a [バグ] pid の再利用で古いファイルが残り、新しい URL を書き出せない**: 強制終了で残った `<名前>-<N>.json` があり、新しいラッパーが同じ pid N を得ると、掃除は「動いている」と判定して消さず、`wx` が `EEXIST` で失敗して古い `editorUrl` が残る。書き出し前の時点では自分の pid のファイルは必ず古いものなので、消してよい
- **L-b [運用] 掃除の失敗で自分の書き出しまで止まる**: `removeStaleInfo` 内の `rmSync` 等の例外が、同じ try の中の書き出しを飛ばす。掃除の失敗は握って起動を続けるとよい
- **L-c [セキュリティ/参考] 既存ディレクトリの権限は 0o700 にならない**: `mode` は新規作成時のみ有効。ファイル自体は 0600 で、他ユーザーはこのディレクトリにファイルを作れないため実害なし。必要なら `chmodSync(dir, 0o700)` を足す（Windows では効かない）
