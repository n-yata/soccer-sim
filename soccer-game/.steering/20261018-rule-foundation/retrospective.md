## 計画と実績の差分
- **壊れたデータの置き方を変えた**: 要求書は fixture を `tests/fixtures/` に置く想定だった。設計で、本物の JSON を1か所だけ変えてテストの中で作る形に変えた（本物を直したときに fixture が古いまま残らないため）。
- **Godot 4 の `OS` には時刻の関数が無かった**: 要求書の `OS.get_ticks` は、検出対象から外した（Godot 3 の API だった）。
- **一括実行の最初に、エディタでの取り込みを足した**: 新しい `class_name` は、取り込むまでテストから見えなかった。ただし取り込みはスクリプト全体をコンパイルしない。構文エラーは、テストの実行時に検出される。
- **禁止依存の検査は、2回のレビューで大きく作り直した**:
  - `extends` を許可リスト方式にした。
  - 完了の記録を付けた。
  - `--self-check` で、全ルールと全行の空振りを確かめるようにした。
  - 当初の設計（カテゴリごとに禁止 API を1つ書いた fixture）では、検出力が足りなかった。

## 学び
- **関数が打ち切られると、既定値が「成功」に見える**: GDScript は、実行時エラーで打ち切られた関数が、戻り値の型の既定値（int なら 0）を返す。外側の処理はそのまま進み、成功の行まで出す。「最後まで走ったときだけ出る行」を一番外側に1つ置くだけでは足りない。打ち切られうる関数ごとに完了を記録して、突き合わせる。
- **自己確認は「ルールが当たったか」ではなく「書き方ごとに検出されたか」で見る**: 1つのルールに複数の書き方を割り当てると、2つ目以降が退行しても、ルール単位の確認は緑のまま。fixture の行に目印を付けて、行単位で確かめる。
- **変異は、入ったことを先に確かめる**: シェルのヒアドキュメント経由で `\\` が `\` に変わり、変異が入らないまま「すべて成功」と出た。testing.md のとおり、該当行を出して変異を目で確かめてから結果を読む。バックスラッシュを含む書き換えは、Write ツールでファイルに書き、`chr(92)` で組み立てる。同じ原因で、文書の `\b` がバックスペース文字に化けた事故もあった（制御文字の検査で見つけて直した）。
- **範囲の検査が守るもの・守らないものを分けて書く**: inf は範囲の比較で弾かれるため、`is_finite` を外してもテストは落ちなかった。`is_finite` が守るのは NaN だけで、NaN は Godot の JSON では作れない。テストのコメントに、何を確かめていて何を確かめていないかを正直に書いた。

## 申し送り
- 禁止依存の検査:
  - 複数行の文字列（`"""`）を行単位でしか扱えない。
  - `RandomNumberGenerator` を変数に入れてから `new()` する経路を検出できない。
  - CI に載せるときは、Godot の呼び出しを `timeout` で包む。
- アルゴリズム2で配置を書き換える処理を作るときは、新しい値を作る形を守る。
  - `PitchArea` の `lane`・`zone` は公開変数で書き換えられる。
  - `TeamLayout.at_base` は、基本エリアと現在エリアで同じ `PitchArea` を共有している。
  - `PlayerState.duplicate_deep()` は、`base_area` が null だと落ちる。
- 書き出した APK の起動の確認は、メインシーンを作る「動く骨格」の作業で行う（開発環境の構築からの持ち越し）。
- NFR-14 の「判定例・エッジケースとテストの対応表」は、テスト仕様書（`docs/specs/4_unit-test/`）を作る作業で作る。今回のテストは、アルゴリズム1の範囲を網羅している。
