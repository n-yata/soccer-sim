実装完了日: 2026-10-19

## 何をしたか
- **調整値の読み込み（`ConfigRepository`）**
  - `game/config/match_rule_config.tres`・`cpu_config.tres` を読み、1回読んだら持っておく。
  - 読めない・型が違う・範囲外（NaN・無限大を含む）のときは、初期値を使って `push_error` する。
  - 範囲は、内側にあることを肯定形で確かめる。
- **視点の変換（`ViewConverter`）と画面向けの値**
  - 画面向けの値は `BoardSnapshot`・`RevealView`。
  - 利用者 = HOME、CPU = AWAY。各チームの選手と動きは、そのチーム自身の視点から変換する。選択の運ぶ先・比較エリア・ボール位置は、判定時の攻撃側の視点から変換する。
  - 開示では、利用者の役割と人数の向きを、攻撃側かどうかで入れ替える。
- **相手（`OpponentPolicy`・`CpuOpponent`）**: CPU の選択（`CpuPlanner`）に、注入された乱数と調整値を渡す。
- **`MatchController`**
  - 試合の開始: キックオフ側と試合 ID の乱数部は、注入された乱数で決める。
  - 1ターンの確定と開示。
  - 段階ごとの画面の要求: S-04・S-05・S-06。
  - 方式の選び直しとハーフタイム（CPU 側も選び直す）。
  - CPU の手が選べないとき: 開発時は `assert`、書き出し版は先頭の手に置き換える。
  - 試合前の問い合わせのガード。
  - 開示の確認待ちのガード。
- **`App` に組み込んだ**: 乱数生成器を1つ作り、CPU と進行で共有する。試合を最後まで進めて結果の画面を頼むところまで、App 経由で確かめた。

## 計画と実績の差分
- **開示の確認待ちという状態を、設計で見落としていた**。設計では、進行段階（`MatchStage`）だけで受け付けを決めていた。けれど「ターンは解決したが、利用者がまだ開示を見ていない」という状態は、ドメインの段階には現れない。UI の手前の層が持つべき状態で、コミット前レビューで初めて指摘された。
- **盤面に出す動きを、ターンの記録から切り離した**。直前のターンの記録の動きをそのまま出していたため、配置を作り直した後も前の矢印が残る形になっていた。
- **CPU の手の置き換えの期待値**を、実装の写し（テスト用ヘルパー）から手で導いた値（PRESS・D-L1）に変えた。導出はテストのコメントに残した。

## 学び
- **ドメインの状態機械とアプリケーションの状態機械は別物**。ドメインの段階（TURN / STYLE_CHANGE / HALFTIME）が正しくても、「開示を見せている途中」は画面側の段階なので、そこでは守れない。UI に近い層を作るときは、「利用者がまだ見ていないもの」が無いかを状態として数える。
- **「直前のもの」を返す値は、何がリセットするかを決めておく**。前のターンの動きは、配置が作り直されると意味を失う。保持する値ごとに「何が起きたら無効になるか」を設計に書く。
- **変異で Red を確かめる**。gdUnit4 は、スイートの中で失敗が出ると、以降のテストの件数が減る。そのため、先に書いたテストのうち、どれが落ちたかを1回の実行で見分けられないことがある。実装の後に「その行を消す変異」を入れ、各テストが本当に効いていることを確かめた。
