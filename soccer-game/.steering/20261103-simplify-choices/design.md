# 設計

要求は `requirements.md`。ここでは実装の方針と、要求の「未決事項」の決め方を書く。

## 方針: 「ルール上選べる手」と「画面に出す手」を分ける

| | 役割 | 使う所 |
|---|---|---|
| `MoveRules.options_for`（今のまま。手を足す） | ルール上選べる手の全部（手ごとに運ぶ先の一覧） | `MatchRules.resolve_turn` の確かめ、`MatchController._cpu_choice` の確かめ（チュートリアルの決め打ちの相手の手も通すため） |
| `MoveMenu.options_for`（新規） | 画面に出す手。手ごとに運ぶ先は0か1件。ゲームが選んだもの | 利用者の手（`MatchController.user_options`・`user_hints`・`user_preview`・`submit_turn` の確かめ）、CPU の手（`CpuPlanner`） |

`MoveMenu` は `MoveOptions` を返す。手ごとに運ぶ先が1件になるだけなので、ヒント（`MoveHints`）・プレビュー・視点の変換（`ViewConverter`）・確かめ（`MoveRules.is_allowed`）は今の関数がそのまま使える。

## 手の区分値（`GameEnums`。末尾に足し、既存の番号を変えない）

- `PlayType` に `BACK_PASS` を足す。
- `DefenseAction` に `CLOSE_DOWN`（ボールに寄せる）と `BLOCK_SHOT`（シュートコースを塞ぐ）を足す。
  - 選手の動きはどちらもプレスと同じ（`DefenseMover` は COVER 以外をプレスとして動かす）。
  - 違いは読みの扱いだけ（下の「判定」）。
- 既存の手（`THROUGH_PASS`・`LONG_BEHIND`・`SWITCH`）は残す。
  - ゲームがショートパス・ロングパスの中身として選び、判定・記録・開示ではその手の名前で出る。
  - 中断データ・戦績の手の名前はそのまま読める（未決事項「中断データの扱い」はこれで解決し、作業は要らない）。

## ボタン（枠）と手の対応

| 枠 | 手 | 並び |
|---|---|---|
| ショートパス | `SHORT_PASS` か `THROUGH_PASS` のどちらか | ① |
| ロングパス | `LONG_BEHIND` か `SWITCH` のどちらか | ② |
| ドリブル | `DRIBBLE` | ③ |
| 4つ目 | `SHOT`（ペナルティエリア）か `BACK_PASS`（それ以外） | ④ |
| パスコースを切る | `PRESS`（ショートパスの予測先） | ① |
| 背後を埋める | `COVER`（ロングパスの予測先） | ② |
| ボールに寄せる | `CLOSE_DOWN`（ボールのエリア） | ③ |
| シュートコースを塞ぐ | `BLOCK_SHOT`（ボールのエリア） | ④ |

- 枠の対応は `MoveMenu.slot_actions(family, action)`（同じ枠の手の一覧）で持つ。チュートリアルの絞り込み（`allowed_actions`）も枠で効かせる。たとえば `SHORT_PASS` を許せば `THROUGH_PASS` も通る。
- ボタンの並びは上の①〜④。攻撃と守備で、読みが対応する手を同じ番号にそろえる。

## 選べる手の追加（`MoveRules`）

- `BACK_PASS`: ボールがペナルティエリアの外にあり、運ぶ先に味方がいて、運ぶ先がボールより1〜2列後ろでレーン差が2以内（ショートパスの届く範囲の後ろ）。
- `CLOSE_DOWN`: 運ぶ先はボールのエリア。そのエリアへプレスできる（守備側から見て上下左右に味方がいる）とき。
- `BLOCK_SHOT`: `CLOSE_DOWN` の条件に加えて、ボールがペナルティエリアにあるとき。
- `defense_options` はボールのエリアを受け取るようにする。

## ゲームが行き先を選ぶ規則（`MoveMenu`。未決事項「いちばん有利の基準」「ショート・ロングの中身の決め方」）

**攻撃・カウンター**: 枠の手の候補（運ぶ先ごとの `MoveHints` のヒント）を、次の順で比べていちばん上のものを選ぶ。

1. 今の配置のままオフサイドにならない
2. マーク注意（スルーパスで、相手が何もしなくても守備が入ってくる）でない
3. 人数差（自分 − 相手。スルーパスも、走り込んだ後の人数で比べる）が大きい
4. 前進の列数（運ぶ先の列 − ボールの列）が大きい（バックパスでは、近い後ろが先になる）
5. 候補の順（手の enum の順、運ぶ先は `PitchArea.all()` の順）が先

- 同じ局面なら同じ手になる（決定的）。
- 要求にあったバックパスの「周りの相手がいちばん少ないエリア」は、同じ比べ方（人数差）にそろえる。

**守備**: 攻撃側のメニュー（`MoveMenu.options_for(state, 保持側)`）から予測先を取る。

- パスコースを切る: 攻撃のショートパスの枠の運ぶ先へ `PRESS`。
- 背後を埋める: 攻撃のロングパスの枠の運ぶ先へ `COVER`。
- 予測先でその手を選べないとき（隣に味方がいない、カバーの条件を満たさない）は、選べる運ぶ先のうち予測先にいちばん近いもの（`steps_to`。同じなら候補の順）にする。選べる運ぶ先が1つも無いか、攻撃にその枠が無いときは、ボタンを出さない（未決事項「背後を埋めるとカバーの条件」）。
- ボールに寄せる・シュートコースを塞ぐ: 選べればボールのエリア。

**トランジション**: 保持は常に。カウンターは攻撃と同じ規則で1件。即時奪回・リトリートは今のまま。

## 判定（`OpenPlayJudge`）

- 読みの段階（`detail.read`）を、手を見て決める。
  - 攻撃がシュート: 守備が `BLOCK_SHOT` ならぴったり、それ以外は外れ。
  - 攻撃がドリブルで、守備が `CLOSE_DOWN`: ぴったり。
  - それ以外: 今の `read_of`（エリアで比べる）。`CLOSE_DOWN`・`BLOCK_SHOT` の運ぶ先はボールのエリアなので、パスには効かない。
- `BACK_PASS`: 守備の手を適用した後、判定せず `NO_CONTEST`（内訳なし）を返す。
  - 試合進行（`MatchRules._ball_after`）は、`NO_CONTEST` で保持側の手に運ぶ先があれば、そこへボールを移す。
  - 振り返りでは数えない（`NO_CONTEST` は今も除外）。
  - 結果の札は「判定なし」。判定理由は「バックパスで作り直し」。

## 画面（`MatchBoardPanel`・`ChoicePanel`・`MatchTexts`）

- 状態 `SELECT_TARGET` をなくす。手を押すと、ゲームが選んだ運ぶ先で `READY` になる。
  - 盤面の選択・矢印・プレビュー・説明を出す。
- ターンの頭に、自分の手の行き先を盤面にすべて出す。
  - 選べるエリアの枠と、札（①〜④。ヒント ON なら人数差の札も添える）。
  - 盤面のエリアを押すと、そのエリアを行き先にする手を選ぶ。
  - 相手の手の行き先は出さない。
- `ChoicePanel` は選べる手だけを並べる（選択不可のボタンは出さない）。ボタンの文言は次の通り。
  - 1行目: 番号と枠の名前（例「① ショートパス」）。
  - 2行目: 行き先（例「→ 中盤（敵陣）・左HS」）。中身の手が枠の名前と違えば、手の名前を添える（例「スルーパス → 敵陣・中央」）。
  - 3行目: ヒントの札（ヒント ON）。
  - 守備は1行目が守備の手の名前（「パスコースを切る」など）、2行目が守る位置。
- 手の名前（`MatchTexts.ACTION_NAMES`）: 守備は PRESS「パスコースを切る」・COVER「背後を埋める」・CLOSE_DOWN「ボールに寄せる」・BLOCK_SHOT「シュートコースを塞ぐ」にする。攻撃は BACK_PASS「バックパス」を足す。
- 選んだ手の一言（`MatchTexts.target_rule`）は、新しい守備の手とバックパスの説明を足して残す。
- ボールの軌道（`BallFlight`）: `BACK_PASS` はグラウンダー。

## CPU（`CpuPlanner`）

- 候補を `MoveMenu.options_for` にする。評価値・加点・確率の式は変えない。
- 方式の癖: 守備の手は COVER 以外をプレスとして扱う（マンツーマンが好む）。`BACK_PASS` は保持型が好む手に入れない（加点なし）。

## チュートリアル（`tutorial.json`）

- 攻撃・守備・シュートの説明文を、行き先を選ばない操作に合わせて書き直す。
- 守備の段階の `allowed_actions` を `CLOSE_DOWN`・`PRESS`・`COVER` にする。
- 決め打ちの相手の手は、ルール上選べる手（`MoveRules`）で確かめるので、今のままでよい。
