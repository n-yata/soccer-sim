## 1. はじめに

### 1.1 目的

本システムが満たすべき非機能要件を定義し、関係者間で合意することを目的とする。各要件は測定可能な
目標と測定方法を伴い、設計・実装・テスト工程で検証する。

本プロダクトの価値の中核は「ルールが正しく、結果が判断に帰着すること」にある。そのため、性能よりも
**判定の決定性・対称性・偏りのなさと、それをテストで検証し続けられること**（§4・§6）を重視する。

### 1.2 分類方針

本書は IPA「非機能要求グレード」の大分類を参考に、本プロジェクトに該当する観点を定義する。スコープに
照らして限定的・対象外となる観点も、「なぜそうなのか」を明示する（§8）。

| 大分類（IPA 非機能要求グレード相当） | 本書での扱い | 該当節 |
|---|---|---|
| 性能・拡張性 | 定義する（判定の応答・盤面の動き・起動・サイズ・メモリ） | §3 |
| 信頼性・データ整合性（可用性含む） | 定義する（判定の決定性・対称性・偏りのなさ、保存データの保全・互換）。可用性は対象外 | §4 |
| セキュリティ | 定義する（外部通信なし・個人情報なし・シークレット管理） | §5 |
| 運用・保守性・テスト容易性 | 定義する（本プロジェクトの主眼） | §6 |
| ユーザビリティ | 定義する（試合時間・操作・視認性・画面の向き・学習効果の測定） | §7 |
| 移行性・システム環境 | 限定的（対応環境と、アプリ更新時の保存データの互換のみ定義。旧システムからの移行は対象外） | §4・§8 |

## 4. 信頼性・データ整合性

| NFR-ID | 要件 | 目標・基準 | 測定方法 |
|---|---|---|---|
| NFR-05 | 判定の決定性（FR-05） | 同じ入力（局面・ボール位置・両者の配置・陣形・方式・選択）からの判定結果が 100% 一致する | 自己対戦（§2 #4）で記録した全ターンの入力を、もう一度判定して結果を突き合わせる自動テスト |
| NFR-06 | 判定の対称性（FR-05） | チーム（陣形・方式・選択・攻撃方向）を入れ替えた入力の結果が、100% 鏡写しになる | `functional-overview.md` の判定例すべてと、自己対戦の全ターンについて、入れ替えた入力で判定して結果を突き合わせる自動テスト |
| NFR-07 | 陣形・方式の偏りのなさ（FR-02） | ①他の15通りすべてに勝ち越す組み合わせが存在しない。②どの組み合わせにも、勝ち越せる相手と負け越す相手がそれぞれ1つ以上ある | 自己対戦（§2 #4）の総当たりを固定シードで実施し、組み合わせごとの対戦成績表を出力する自動テスト。勝ち越しの判定は「勝ち数 > 負け数」、負け越しは「勝ち数 < 負け数」 |
| NFR-08 | 中断データの保全（FR-14） | 強制終了後、直前に確定した状態から 100% 再開できる（ターンの途中まで進んだ操作は失われてよい）。再開先は中断した画面（`functional-overview.md`「確定事項」の再開先） | ①単体テスト: 保存の書き込み途中で失敗させても、以前の中断データが壊れずに残る（一時ファイルから置き換える方式の検証）。②実機確認: Android 基準端末で、試合中のさまざまな時点（手の選択中・演出中・方式の選び直し中・ハーフタイム）でアプリを強制停止し、計20回すべてで中断した画面から再開できること |
| NFR-09 | 破損した保存データへの耐性 | 破損・改変された保存データ（中断データ・戦績・回答結果・設定）を読み込んでもクラッシュせず、`functional-overview.md`「エラーハンドリング」どおりに処理する（100%） | 壊れた JSON・型の違う値・範囲外の値・空ファイル・大きすぎるファイルを用意し、各保存データについて読み込む自動テスト。戦績・回答結果・設定は、破損時に元のファイルが退避されて残ることも確かめる |
| NFR-26 | アプリ更新時の保存データの互換 | アプリを更新しても、更新前の版で保存した戦績・回答結果・設定を 100% 読み込める（形式のバージョンを見て変換する。`architecture-overview.md`「保存データの形式のバージョン」） | 保存データの形式を変えるたびに、変更前の形式のテスト用データを残し、新しい版で読み込んで内容が保たれることを確かめる自動テスト。あわせて、今の版より新しい形式のデータを読み込んだときに、上書きせずに元のファイルが残ることを確かめる |

**可用性について**: 定めない。端末内で完結するスタンドアロンアプリで、サーバーを持たないため（§8）。

**バックアップ戦略**: アプリとしてのバックアップ機能は持たない。Android の OS 標準のアプリデータ自動
バックアップは無効にする（アプリのデータを外部へ送らないという方針を明確にするため。§5）。保存データの
保全は、一時ファイルから置き換える書き込み方式（NFR-08）で担保する。

## 5. セキュリティ

| NFR-ID | 要件 | 目標・基準 | 測定方法 |
|---|---|---|---|
| NFR-10 | 外部通信をしない（要件定義書 §7 #8） | Android のアプリにネットワークの権限が 0 | リリース用に書き出した AAB のマニフェストの権限一覧を確認する（リリースごと。デバッグ用の書き出しは、リモートデバッグのために権限が付くことがあるため対象にしない）。確かめ方: Android SDK の build-tools の `aapt2 dump permissions`（APK）または `bundletool dump manifest`（AAB）で、`uses-permission` が 0 件であること。開発環境の構築時（2026-10-18、Godot 4.7.2、書き出し設定 `permissions/internet=false`）には、`--export-debug` の APK と、デバッグ用の鍵で署名した `--export-release` の APK の両方で `uses-permission` が 0 件だった |
| NFR-11 | 個人情報を扱わない | 保存データに、氏名・メールアドレス・端末識別子など個人を特定できる情報が 0 | 保存データの項目を `functional-overview.md` のデータモデルと突き合わせるレビュー（データモデル変更時） |
| NFR-12 | シークレットをリポジトリに含めない | Android の署名鍵（アップロード鍵）・その鍵のパスワードのリポジトリへの混入が 0 | ①CI のシークレットスキャン（流出防止の正本。`repository-structure.md`「CI/CD」）。②コミット前レビュー（`review-pre-commit`）のハードコーディング検出。③除外設定（`repository-structure.md`）の確認 |

**セキュリティ上の配慮**:
- **データ保護**: 保存データはゲームの進行データだけで機密性は低い。暗号化はしない（§8）。改変された場合の耐性は NFR-09 で担保する
- **入力検証**: 手の選択はドメイン層でも検証し、選択不可の手を拒否する（`functional-overview.md`「エラーハンドリング」）。保存データの読み込み時は型と範囲を検証する（NFR-09）
- **機密情報の管理**: 署名鍵・認証情報は端末のローカル（リポジトリ外）で管理し、配置ルールは `repository-structure.md` で定める
- **依存の安全性**: 素材・アドオンは調達元とライセンスを台帳で管理する（`architecture-overview.md`「依存関係管理」）

> ハードコーディング検出・OWASP Top 10 等の実装レビュー観点は kit の `reference/rules/code-review.md` を
> 正本とする（本節には数値目標・プロジェクト固有の方針のみを書く）。

## 6. 運用・保守性・テスト容易性

**本プロジェクトの主眼はテスト容易性にある。** ルールの正しさ（判定例・決定性・対称性・偏りのなさ）を、
ルールを変えるたびに自動で検証できる状態を保つ。

| NFR-ID | 要件 | 目標・基準 | 測定方法 |
|---|---|---|---|
| NFR-13 | ドメインロジックの分離 | `architecture-overview.md`「ドメイン層」で禁止した参照が、ドメイン層のスクリプトに 0 | ドメイン層のディレクトリを対象に、禁止している API 名を検索する自動チェック（CI で毎回実行）。検索する API 名の一覧は、そのチェックスクリプト（`tools/check_domain_deps.gd`。`tools/run-tests.sh` から実行する）を正本とする |
| NFR-14 | 判定例・エッジケースのテスト化 | `functional-overview.md` の判定例（JE-01〜JE-07）と、各アルゴリズムの「エッジケース（テスト対象）」の 100% に対応するテストがある | 判定例・エッジケースとテストの対応表（基本設計以降のテスト仕様書で作成）で、未対応が 0 であることを確認する |
| NFR-15 | 自己対戦検証の実行時間 | NFR-05〜07 の自己対戦検証が、開発機で 10分以内に終わる | 自己対戦検証を CLI から実行し、所要時間を記録する |
| NFR-16 | ルール値の外部化 | `functional-overview.md`「確定事項」の「設定値として外部化する値」を、コードに直接書かない（直書き 0） | 設定値ファイルの値を変えたときに挙動が変わることを確かめる自動テストと、コミット前レビュー |
| NFR-17 | ルールと戦術原則の対応（要件定義書 §7 #14） | ①噛み合わせルール・解説の各項目に、戦術原則カタログに実在する原則 ID が付いている（原則 ID なしが 0）。②アプリ内の単純化カタログ・戦術原則の表示データと、`functional-overview.md` のカタログの ID・件数が一致する（不一致が 0） | ①静的データを読み込んで原則 ID を検証する自動テスト。②`functional-overview.md` のカタログの表と、アプリの静的データ（JSON）の ID・件数を突き合わせる自動チェック（`tools/`。CI で毎回実行） |

**検証方針（参考）**: ドメインロジックは gdUnit4 の単体テストで、画面なしで実行する。画面の操作・演出・
保存の実機確認は、Android 基準端末で行う。テストの書き方・カバレッジ方針の型は kit の
`reference/rules/testing.md` を正本とする。

## 7. ユーザビリティ

| NFR-ID | 要件 | 目標・基準 | 測定方法 |
|---|---|---|---|
| NFR-18 | 1試合の所要時間 | プレイテストでの1試合の所要時間の中央値が 10〜15分（ハーフタイム・方式の選び直しを含む。チュートリアルは含めない） | 公開前のプレイテストで、参加者ごとに2試合目以降の所要時間を記録する。外れた場合は1ハーフのターン数・開示で駒を動かす時間（設定値）を調整する（要件定義書 §7.1 #1） |
| NFR-19 | 操作の手段 | Android のタッチだけで、すべての操作ができる。タッチの操作領域は 48dp 以上 | Android 基準端末で全画面の操作を確認するチェックリスト。操作領域の大きさは画面設計（基本設計）で確認する |
| NFR-20 | 色覚に依存しない表示（FR-16） | エリアの優劣（優位・同数・不利）と、チーム（自分・相手）の区別が、色を除いても 100% 判別できる | 試合画面・振り返り画面のスクリーンショットをグレースケールに変換し、すべてのエリアの優劣とチームを判別できるかを確認する |
| NFR-21 | 文字の読みやすさ | 文字と背景のコントラスト比 4.5:1 以上（大きな文字は 3:1 以上） | 画面設計の配色を、コントラスト比の計算ツールで確認する |
| NFR-22 | 学習効果の測定（目標値は要件定義書 §1.5） | 要件定義書 §1.5 の学習効果の KPI を、決めた手順で測定できる | 公開前のプレイテストで、育成年代・アマチュアの選手 合計10名以上に、プレイ前と3試合プレイ後に同じ8問（FR-22 の出題セットの一部）を解いてもらい、正答数の差の平均を求める。あわせて「実戦と違うと感じた場面」を記録する（要件定義書 §7 #17） |
| NFR-23 | 利用状況の測定（目標値は要件定義書 §1.5） | 要件定義書 §1.5 の利用状況の KPI を、アプリに計測機能を持たせずに取得できる | Google Play Console の統計で確認する。アプリ内に解析 SDK を組み込まない（NFR-10） |
| NFR-25 | 画面の向きと表示範囲 | Android の横向き（ランドスケープ）で、アスペクト比 16:9〜21:9 の画面で表示が欠けない。縦向きには回転しない | エミュレーターでアスペクト比 16:9・20:9・21:9 の各画面を用意し、全画面の表示を確認するチェックリスト |

## 8. 対象外・限定対応の観点

スコープに照らし、対象外または限定対応とする非機能観点を、理由付きで明示する。

| 観点 | 扱い | 理由 |
|---|---|---|
| 可用性（冗長化・SLA・障害復旧） | 対象外 | サーバーを持たず、端末内で完結するため |
| 移行性（旧システムからのデータ移行） | 対象外 | 新規構築であり、移行元のデータが存在しないため。なお、アプリ更新時の保存データの互換は NFR-26 で扱う |
| システム環境（対応 OS） | 限定対応 | Android（最小 API レベルは `architecture-overview.md`「環境要件」に記録）のみ。Windows・iOS・macOS は後続マイルストーン（要件定義書 §6.2） |
| 運用監視（クラッシュ収集・利用ログ） | 対象外 | 外部通信をしない方針のため（NFR-10）。不具合の把握は、ストアのレビュー・Google Play Console の標準のクラッシュ情報・プレイテストで行う |
| 保存データの暗号化 | 対象外 | 保存するのはゲームの進行データだけで、個人情報や機密情報を含まないため（NFR-11） |
| 認証・アクセス制御 | 対象外（拡張余地あり） | アカウントを持たないため。アカウント・クラウド保存は後続マイルストーンで、外部通信の方針の見直しとあわせて要件化する |
| 多言語対応 | 対象外 | 表示言語は日本語のみ（要件定義書 §7 #10） |
| ストアへの申告（対象年齢・レーティング・データの取り扱い） | 限定対応（数値目標を持たない） | 全年齢対象（要件定義書 §7 #18）。申告内容は公開申請の準備時にGoogle Play の最新のポリシーで確認する（要件定義書 §7.1 #9）。外部通信なし・個人情報なし（NFR-10・11）が前提になる |

> これらは後続マイルストーンで必要に応じて要件化する。
