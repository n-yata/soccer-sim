## 1. はじめに

### 1.1 本書の目的

本システムの開発にあたり、システムが満たすべき要件を定義し、関係者間で合意することを目的とする。
以降の工程（基本設計・詳細設計・テスト設計・実装）は、本書で採番した要件ID（FR）を起点に進める。

### 1.2 背景

サッカーの選手は、試合中に毎プレー戦術的な判断をしている。どのエリアで数的優位があるか。
寄せたら背後のどこが空くか。ボールを失った瞬間に即時奪回に行くか、撤退するか。ところが、これらを
体系的に学ぶ機会は、育成年代でもアマチュアでも限られている。戦術書や解説動画は「見て・読んで」
理解するものであり、自分で判断し、その結果を確かめる経験にはならない。

既存のサッカーゲームも、この経験の場にはなっていない。多くは選手を直接操作するアクションゲームか、
選手の能力値や育成が勝敗を左右する監督シミュレーションである。勝敗が操作の上手さや能力値に左右され、
**戦術上の判断そのもの**を試す遊びにはなっていない。

先行プロダクトのフォーメーションラボ（リポジトリ `soccer-sim`）は、2つのフォーメーションの
噛み合わせを、ピッチ図と解説で「見て・読んで」理解する学習アプリである。その開発では、能力値と
乱数で試合を疑似計算する機能（試合シミュレーション・リーグ戦・カップ戦・ハーフタイム采配）を
いったん実装した。しかし「結果が戦術理解の目安にならない」との判断で撤去している。戦術を学ぶには、
結果が利用者の判断に帰着することが欠かせない、というのがその教訓である。

本プロダクトは、フォーメーションラボの「見て・読んで」理解する学習を、「自分で選び、試して
確かめる」学習へ進めるものである。現代サッカーの戦術の考え方を、能力値も運も排したルールとして
抽出する。具体的には、5レーン×6列のピッチ分割（2026-10-25 に3ゾーンから6列にした）、攻撃・ネガティブトランジション・守備・
ポジティブトランジションの4局面、フォーメーションと戦い方（守備方式・攻撃方式）の噛み合わせ、
チャレンジ＆カバーである。これを**陣形・戦い方の選択と同時手番の読み合い**として遊べる形にする。

ゲームとして面白くても、間違った戦術を覚えさせては意味がない。実際にプレーする選手は、
現実とのズレにすぐ気づく。そこで本プロダクトでは、**すべてのルールを公開された戦術原則に紐づけ、
表現しきれない部分は単純化として明示する**ことを要件とする（§4.1.4、§7）。

### 1.3 プロダクトビジョン

**このゲームを遊んだ利用者（実際にプレーする選手）が、サッカーの戦術を理解し、自分のプレーの判断に
活かせるようになること**を目指す。

勝敗を決めるのは、ゲーム内の選手の能力値でもサイコロでもない。**試合前と試合中の陣形・戦い方の選択（噛み合わせ）
と、毎ターンの読み合いの判断だけ**で決まる。ターンの結果は、すべて「両者が動いた後に、そのエリアで
何人対何人だったか、背後にカバーがいたか」で説明できる。負けた理由は利用者自身の判断に帰着する。
試合後の振り返りで「なぜ奪われたか」「なぜ崩されたか」を人数と位置の言葉で理解し、「次はこう組み、
こう読む」という再戦の動機と、実戦での判断の手がかりが生まれる。

**プロダクトコンセプト**:
- **戦術原則をそのままルールに**: ルールはすべて公開された戦術原則に紐づく。表現しきれない部分は単純化として明示し、「実戦ではこう」を添える
- **人数で説明できる結果**: 能力値なし・判定に乱数なし。結果は「動いた後の人数差」「守備の読み（制限したエリアと運ぶ先が同じか）」「カバーの有無」だけで確定する
- **噛み合わせと読み合い**: 陣形と戦い方（ゾーン／マンツーマン、保持型／カウンター型）の組み合わせで、どこが空き、どこが薄くなるかが変わる。その上で毎ターン、どこで勝負し、どこで寄せるかを読み合う
- **スキマ時間で完結**: 1試合10〜15分。中断・再開ができ、スマートフォンでいつでも遊べる

### 1.4 学習目標

遊び終えた利用者が、次の4つをできるようになっていることを目標とする。以降の工程（ルール設計・解説・
理解度チェック・プレイテスト）は、本 ID で学習目標を追跡する。

| ID | 学習目標 | できるようになること |
|---|---|---|
| LG-1 | 位置的・数的優位を見つける | どのエリア（特にハーフスペース・逆サイド）で数的優位があるかを見つけ、そこへボールを運べる |
| LG-2 | チャレンジ＆カバーとスライド | 寄せたら背後や逆サイドが空くことを理解し、どこで寄せ、どこを捨てるかを判断できる |
| LG-3 | トランジションの判断 | 奪われた瞬間に即時奪回か撤退か、奪った瞬間にカウンターか保持かを、人数と位置から判断できる |
| LG-4 | 噛み合わせ | 自分と相手の陣形・戦い方から、試合前に「どこが空き、どこが薄いか」を予測できる。相手を見て修正策を立てられる |

> **扱わない学習内容**: 質的優位（個の能力で上回ること）。能力値を持たない設計のため表現できない。
> 単純化カタログ（`functional-overview.md`）に明記する。

## 2. システム概要

### 2.1 対象利用者（ペルソナ）

一般公開の無料ゲームとして、**実際にサッカーをプレーしている選手**を主な対象とする。MVP は1台の
端末で1人が遊ぶ（1人 vs CPU）前提とし、アカウントやマルチユーザーの概念は持たない。

#### プライマリペルソナ: 育成年代の選手（中学・高校生、部活・クラブ所属）

- 週に数回チームで練習し、週末に試合がある。指導者から「数的優位を作れ」「スライドしろ」と言われるが、なぜそうするのかを体系的に理解しきれていない
- 移動中や自宅では Android スマートフォンを使う
- **現在の課題**: 戦術の言葉は聞いたことがあっても、試合中にどこを見て何を判断すればいいかが結びついていない。戦術書は難しく、試して確かめる場がない
- **期待する解決策**: 自分で陣形・戦い方・毎プレーの判断を選び、その結果を人数と位置で確かめられる。負けた理由がわかり、次の練習や試合で意識することが見つかる
- **典型的なワークフロー**: 練習帰りの電車で1試合（10〜15分）。途中で降車したら中断し、帰宅後に再開する。振り返りで、どの局面で崩されたかを確認する

#### セカンダリペルソナ: 大学・社会人・アマチュアの選手（18〜40代）

- 競技経験は長いが、戦術を体系的に学んだことは少ない。観戦で見聞きした戦術を自分のチームに持ち込みたい
- 通勤中も帰宅後も Android スマートフォンを使う
- **現在の課題**: 経験則ではわかっていても、言語化して仲間と共有できない。自チームの陣形や戦い方を変えたらどうなるかを試す場がない
- **期待する解決策**: 陣形と戦い方の噛み合わせを試し、「なぜそうなるか」を人数と位置で説明できるようになる
- **典型的なワークフロー**: 週末の試合の前に、相手の陣形を想定して何試合か遊び、ハーフタイムの修正策を考える

> いずれのペルソナも実際にプレーしているため、現実とのズレに敏感である。単純化を明示する要件
> （FR-23）と、ルールを戦術原則に紐づける制約（§7 #14）は、このペルソナから導かれる。

### 2.2 システム構成の概要

端末内で完結するスタンドアロンのネイティブアプリとする。サーバー・外部通信は MVP では持たない（§7 #8）。
技術選定・レイヤー構成の正本は `architecture-overview.md`、モジュール構成の正本は `functional-overview.md`。

## 3. 利用シナリオ

詳細なユースケース定義は `functional-overview.md`「ユースケース一覧」に引き継ぐ。

### 3.1 初回起動からチュートリアル

初めて起動した利用者は、チュートリアルで、ピッチ（30エリア）、4局面のサイクル、同時手番の読み合い、
陣形・方式による選手の動き方を体験する。チュートリアルの最後に、このゲームが表現していること・
していないこと（単純化）を確認する。その後タイトル画面に戻り、CPU との試合を始められる。

### 3.2 CPU との1試合

利用者は、解説で各フォーメーションと方式の特徴を確かめてから、陣形・守備方式・攻撃方式を選ぶ。
CPU も同時に選び、試合開始時に両者の選択が開示される。試合画面では、両者の噛み合わせ（エリアごとの
数的優位・不利）と、相手の現在の方式がピッチ上に表示される。

各ターン、利用者は局面に応じた行動を CPU と同時に選ぶ。攻撃では運ぶ先のエリアとプレー種別を、守備では
寄せるエリアとプレス／カバーを、トランジションでは即時奪回／リトリートまたはカウンター／保持を選ぶ。
双方の選択が開示され、方式に従って選手が動いた後の人数差・守備の読み・カバーの有無から、ボールの位置・保持・局面が
確定する。開示時には「何人対何人だったか、背後にカバーがいたか」が示される。

得点が入ると、キックオフ前に両者が方式を選び直せる。前半を終えると、ハーフタイムに前半の結果と相手の
陣形・方式を踏まえて、陣形と方式を選び直す。後半終了時点の得点で勝敗が決まる。試合後の振り返りで、
どのエリア・どの局面で優位に立てたか、崩されたかを確認する。結果は戦績に記録される。

### 3.3 理解度チェック

利用者は、タイトル画面から理解度チェックを開き、学習目標に対応した場面問題を解く。自分がどの学習目標を
理解できているかを確かめられる。結果は端末内にだけ保存される。

### 3.4 中断と再開

試合中にアプリを閉じても、次回起動時に中断した試合を続きから再開できる。

## 4. 機能要件

### 4.1 機能一覧

機能要件を FR-ID で採番する。以降の工程（設計・テスト）は本 ID で要件を追跡する。優先度は
P0=必須 / P1=重要 / P2=できれば、とする。優先度と公開の関係は §6.3「リリース判定基準」で定める。

#### 4.1.1 試合進行

| FR-ID | 機能 | 概要 | 優先度 |
|---|---|---|:--:|
| FR-01 | 試合開始 | CPU 対戦の試合を開始する。開始時に両者が同時・秘匿で、陣形・守備方式・攻撃方式を選ぶ | P0 |
| FR-02 | フォーメーションと噛み合わせ | 4種のフォーメーション（4-4-2・4-3-3・4-2-3-1・3-5-2）を提供する。各フォーメーションは30エリアの基本配置を規定する。両者の陣形・方式の組み合わせによって、エリアごとの数的優位・不利が決まる | P0 |
| FR-03 | 攻撃・守備の同時手番 | 攻撃局面ではプレー種別を、守備局面では守り方（何を読むか）を、両者が同時に選ぶ。行き先はゲームが決めて選ぶ前に見せる（2026-11-03） | P0 |
| FR-04 | トランジションの同時手番 | ボールを失った側は即時奪回／リトリートを、奪った側はカウンター／保持を、同時に選ぶ | P0 |
| FR-05 | ターン判定と局面遷移 | 方式に従って選手が動いた後の人数差・守備の読み・カバーの有無から、乱数を使わずにターンの結果（ボール位置・保持・次の局面）を確定する | P0 |
| FR-06 | シュートと得点 | ペナルティエリア（6列目の中央・ハーフスペースの3マス）でシュートを選べ、そのエリアで人数が上回れば得点となる（同数は、守備にぴったり読まれていなければ得点。隣の読みはシュートに効かない）。得点後はキックオフから再開する | P0 |
| FR-07 | 試合時間とハーフ | 前半・後半をそれぞれ固定ターン数で進行し、最終ターンで続いている攻撃はアディショナルタイムとして続ける。ターン数とアディショナルタイムの最大ターン数は設定値として外部化する | P0 |
| FR-08 | ハーフタイムの選び直し | ハーフタイムに、前半の相手の陣形・方式を踏まえて、両者が同時・秘匿で陣形と方式を選び直す | P0 |
| FR-09 | ターン結果の可視化 | 毎ターン、双方の選択・選手の動き・判定理由（人数差・カバーの有無）・ボールの移動・局面の変化を表示する | P0 |
| FR-10 | 試合結果 | 後半終了時の得点で勝ち・負け・引き分けを判定して表示する | P0 |
| FR-11 | CPU 対戦相手 | CPU が局面に応じて行動を、節目で陣形・方式を選ぶ（強さは1種類） | P0 |
| FR-20 | 守備方式・攻撃方式 | 守備方式（ゾーン／マンツーマン）と攻撃方式（保持型／カウンター型）を提供する。方式は選手の動き方を規定する | P0 |
| FR-21 | 試合中の方式変更 | 得失点後のキックオフ前に（ハーフの最終ターンの得点を除く）、両者が同時・秘匿で方式を選び直せる。相手の現在の方式は常に表示する | P0 |
| FR-24 | ターン結果の盤面での表示 | 手を選ぶのも結果を見せるのも作戦ボード（縦向きのピッチを斜めから見た半3D）。開示後は、判定前の位置から判定時の位置へ（プレー）、続けて次のターン開始時の位置へ（詰め直し）、駒とボールが2拍で動いて見せる（0.7 で 3D 演出から置き換えた。2026-11-03 に2拍にした） | P0 |

#### 4.1.3 戦術学習

ビジョン（§1.3）と学習目標（§1.4）を実現する機能群。

### 4.2 機能詳細と受け入れ基準

中核ロジック（座標からのエリア人数の導出、方式による動き方、プレス・カバーの移動、ターン判定、
トランジション、シュート）の仕様の正本は `functional-overview.md`「アルゴリズム設計」である。
本節では再掲せず、外部から検証できる振る舞いだけを受け入れ基準として定める。

#### FR-01 試合開始

- タイトル画面から CPU 対戦を選び、陣形・守備方式・攻撃方式を選択すると試合が始まる
- CPU の陣形・方式は、利用者が確定するまで表示されない。両者の確定後に同時に開示される
- CPU は利用者の選択を参照せずに自分の陣形・方式を決める（同時手番の公平性）
- 前半のキックオフ側（先攻・後攻）は試合開始時にランダムに決まり、後半は前半と反対側がキックオフする
- 試合開始時のスコアは 0-0、ターンは前半1ターン目、局面はキックオフ側の攻撃局面である
- 中断中の試合がある状態で新規試合を始めようとすると、中断データが破棄される旨の確認が表示される

#### FR-02 フォーメーションと噛み合わせ

- 4-4-2・4-3-3・4-2-3-1・3-5-2 の4種のフォーメーションを選べる
- 各フォーメーションについて、30エリアの基本配置（人数）を選択画面で確認できる
- 30エリアの基本配置は、フォーメーションラボから移植した選手配置（座標）から導出する（導出規則の正本は `functional-overview.md`）
- 両者の陣形・方式・ボール位置から、30エリアそれぞれの数的優位・同数・不利が一意に定まる
- 同じ局面・同じ選択でも、陣形・方式の組み合わせが異なれば判定結果が変わりうる（具体的な組み合わせは `functional-overview.md` のテストケースで示す）
- どの陣形・方式にも、有利になる相手と不利になる相手がある。すべての相手に対して一方的に有利な組み合わせを作らない（組み合わせの検証方法は `functional-overview.md` で示す）

#### FR-03 攻撃・守備の同時手番

- 攻撃側は「プレー種別」を選ぶ。手はショートパス／ロングパス／ドリブルの3つと、4つ目（ペナルティエリアではシュート、それ以外ではバックパス）。行き先はゲームが手ごとにいちばん有利なエリアを選び、選ぶ前にボタンと盤面で見せる。ショートパスには前の空いたエリアへのスルーパスを、ロングパスには相手最終ライン背後への1本とサイドチェンジを含み、どれにするかもゲームが選ぶ（2026-11-03。シャビの判断「選択をよりシンプルにしたい」。それまでは運ぶ先のエリアも選んでいた。規則の正本は `functional-overview.md` アルゴリズム3「画面に出す手」）
- バックパスは後ろの味方へ戻す手で、判定せず必ず通る。守備は読めず、代償は前に進めず1ターンを使うこと（2026-11-03）
- スルーパスは、前の空いたエリアへも出せ、近くの味方が走り込んで受ける。人数に関係なく、守備に運ぶ先をぴったり読まれるか、守備の選手が運ぶ先へ入ってくれば（2026-10-28）奪われ、そうでなければ通る（2026-10-25 に追加。規則の正本は `functional-overview.md` アルゴリズム3・5）
- 前へのパス（スルーパス・前へのショートパス・背後へのロングボール）は、受け手がパスの時点で守備の最終ライン（守備側のいちばん自陣ゴールに近い選手の列。ボールがそれより前ならボールの列）より前の列にいればオフサイドで、守備側のボールになる。ラインは守備の手を出した後の配置で決まり、最終ラインの選手をプレスで前へ寄せれば上がる（オフサイドトラップ）。2026-10-25 に追加（規則の正本は `functional-overview.md` アルゴリズム5）
- 守備側は守り方を選ぶ。パスコースを切る（相手のショートパスの行き先へ隣接エリアから1人寄せる）／背後を埋める（相手のロングパスの行き先の背後へ1人下げる）／ボールに寄せる（ボールを持つ選手へ寄せ、ドリブルを読めば運ばれる前に奪う）と、ペナルティエリアではシュートコースを塞ぐ。守る位置はゲームが予測して選ぶ（2026-11-03）
- 選べる手は、ボールの現在位置と選手の配置によって制限される（例: 味方のいないエリアへはパスを出せない。スルーパスは、近くの味方が走り込めれば空いたエリアにも出せる）。選べない手はボタンに出さない（2026-11-03 に、選択不可として表示する形から変えた）
- 自分の手の行き先だけを見せ、相手の手の行き先は見せない
- プレスで寄せた選手は、配置区間が終わるまで（キックオフ、またはトランジションターンが終わって次の攻守ターンが始まるまで）元のエリアに戻らない
- 両者が選び終えるまで、相手の選択は表示されない

#### FR-04 トランジションの同時手番

- ボール保持が入れ替わった直後のターンは、トランジション局面になる
- ボールを失った側は即時奪回／リトリートを、奪った側はカウンター（運ぶ先のエリアも選ぶ）／保持を、同時に選ぶ
- 即時奪回は、ボール周辺の人数で相手を上回れば奪い返せる
- リトリートを選んだ側は、基本配置＋守備方式の位置へ1マス近づいた配置で判定される（一気には戻れない。2026-10-24）。保持を選んだ側は、判定時は直前の配置のまま（即時奪回との比較に使う）で、判定後は今の位置から攻撃を始め、方式の位置へ1マスずつ近づく
- 攻撃方式によって振る舞いが変わる。保持型は失った瞬間にボール周辺の人数が多く、カウンター型はカウンターを選んだ瞬間に前線へ人が飛び出す（具体的な規則の正本は `functional-overview.md`）
- トランジションの判定結果に応じて、次の局面が決まる

#### FR-05 ターン判定と局面遷移

- ターンの結果は「方式とその手に従って両者が動いた後の、比較エリアでの人数差」で決まる。上回れば攻撃成功、下回ればボールロスト
- 選手が1ターンに動けるのは、隣のエリア（斜めを含む周り8エリア）まで。選手の位置はターンをまたいで持ち越し、方式の動き（スライド・マーク・リトリートなど）も1マスずつ進む。例外はキックオフで、全員を、陣形を自陣に縮めた位置に置く（2026-10-24。以前は位置を毎ターン計算し直していて、選手が2マス以上一気に動くことがあった。2026-10-25 に、キックオフで相手陣に駒がいないよう自陣に縮めた）
- シュート・スルーパス以外の手で、守備が攻撃の運ぶ先を読んでいたら、攻撃は2人以上多くなければ成功しない（読んで寄せた守備は、1人多いだけの攻撃なら奪える）。運ぶ先の隣（同じ列でレーンが1つ隣。ボールのエリアは除く）を読んでいたら、攻撃は1人以上多くなければ成功しない（同数なら奪える。2026-10-24 に追加）。シュートは人数が上回れば読まれていても得点、同数ならぴったり読まれていなければ得点になる（シュートの読みは、守備がボール位置を制限したこと。隣の読みはシュートに効かない）
- 同数のときは、守備側の背後（比較エリアから守備側ゴール方向へ1マス）に余っている守備者がいれば膠着、いなければ攻撃成功とする（チャレンジ＆カバー原則）。GK は背後のカバーに数えない
- 2026-10-24 に変更（ゲームバランスの見直し。CPU 同士の試合で 1試合 約0.3点・攻守の入れ替わり 約3回だったため）: 読みの規則を足し、GK のカバーをやめ、シュートの同数の扱いを変えた。詳細は `functional-overview.md` アルゴリズム5
- 判定に乱数を使わない。同じ「局面・ボール位置・両者の配置・両者の陣形・方式・選択」からは、常に同じ結果が得られる
- 判定結果として、ボールの位置（エリア）、ボール保持側、次の局面、両者の選手配置が一意に定まる
- 判定は両チームに対して対称である。利用者と CPU の陣形・方式・選択・攻撃方向をそっくり入れ替えると、結果も鏡写しに入れ替わる
- プレー種別どうし・守備の手どうしの抽象的な相性（じゃんけん的な有利不利）は持たない。読みの当たり外れは、人を動かしたエリアの人数と、上の読みの規則（制限したエリアと運ぶ先が同じか）として結果に現れる（2026-10-24 までは、読みが当たったことへのボーナスを持たないとしていた）
- 判定ロジックは `functional-overview.md` の判定例（テストケース）のすべてについて、記載どおりの結果を返す

#### FR-06 シュートと得点

- シュートは、ボールがペナルティエリア（6列目の中央・ハーフスペースの3マス）にあるときだけ選べる（大外と5列目からは直接打てない。2026-10-25 に5・6列目から絞った）
- そのエリアで攻撃側の人数が上回っていれば得点となり、失点した側のキックオフから再開する。ただしハーフの最終ターンの得点は除く。前半の最終ターンの得点なら、得点を反映してハーフタイムへ進む（後半のキックオフ側は失点側ではなく、前半と反対側）。後半の最終ターンの得点なら、得点を反映して試合結果へ進む（正本は `functional-overview.md` アルゴリズム7）
- 同数で守備にぴったり読まれていた場合と、下回っていた場合は GK・守備に止められ、相手ボールとなって相手のポジティブトランジションから再開する。同数でも、ぴったり読まれていなければ得点になる（2026-10-24 に変更。それまでは同数以下をすべて阻止にしていた。同日に追加した隣の読みは、シュートには効かない）

#### FR-07 試合時間とハーフ

- 前半・後半はそれぞれ設定値のターン数で終了する
- 規定の最終ターンを終えた時点で攻撃が続いていれば、アディショナルタイムとして、シュートするかボールを失うまで続ける。最大ターン数は設定値で、使い切ったらハーフを終える（2026-10-24。`functional-overview.md` アルゴリズム7）
- ターン数とアディショナルタイムの最大ターン数はコードに直接書かず、設定値として変更できる（テストプレイで調整するため。§7.1 参照）
- 前半終了時にハーフタイムへ、後半終了時に試合結果へ遷移する

#### FR-08 ハーフタイムの選び直し

- ハーフタイム画面に、前半のスコア・相手の前半の陣形と方式・前半の噛み合わせを表示する
- 利用者は陣形・守備方式・攻撃方式を、それぞれ変更するか維持するかを選べる。CPU も同時に選び、後半開始時に両者の選択が開示される
- 後半は両者が選んだ陣形・方式で判定される
- 陣形はハーフタイム以外では変更できない

#### FR-09 ターン結果の可視化

- 各ターンの開示時に、両者の選択を並べて表示する
- 方式と手によって選手がどう動いたか（スライド・マークの追従・プレスで寄せた選手・カバー）を表示する
- 判定の理由として、比較エリアで何人対何人だったか、同数の場合は背後にカバーがいたかを表示する
- ボールの移動先、保持の入れ替わり、次の局面がピッチ上で確認できる

#### FR-10 試合結果

- 後半最終ターン（アディショナルタイムがあればその最後のターン）終了時の得点で、勝ち・負け・引き分けを判定する（延長戦・PK戦は行わない）
- 結果画面に最終スコアを表示する
- 結果画面からタイトルへ戻れる

#### FR-11 CPU 対戦相手

- CPU は各局面で、ルール上選べる選択肢の中から行動を選ぶ（選べない行動は選ばない）
- CPU は試合開始時とハーフタイムに陣形と方式を、得失点後には方式だけを選ぶ（陣形はハーフタイム以外で変えられない。§7 #7）
- CPU は利用者の選択を判定前に参照しない（同時手番の公平性）
- CPU の行動選択には乱数を用いてよい（同じ局面で常に同じ手を選ぶと、利用者が必勝パターンを見つけて読み合いが成立しなくなるため）。乱数を用いるのは CPU の選択だけで、ターン判定には用いない

#### FR-12 チュートリアル

- 初回起動時にチュートリアルへの導線が表示される
- タイトル画面からいつでもチュートリアルを再実行できる
- ピッチ構造・噛み合わせ・4局面・同時手番・方式による動き方・ターン判定（人数差とカバー）・シュートの各要素を、少なくとも1回ずつ操作して体験できる
- 最後に、このゲームが表現していること・していないこと（FR-23）を示す

#### FR-13 戦績の記録・閲覧

- 試合終了時に、日時・使用した陣形と方式・スコア・勝敗を記録する
- 戦績画面で、試合の一覧（新しい順）と通算の勝ち・負け・引き分け数を表示する
- 中断のまま破棄された試合は戦績に記録しない

#### FR-14 中断・再開

- 試合中にアプリを終了（強制終了を含む）しても、直前に確定したターンまでの状態が保持される
- 次回起動時に中断中の試合があれば、再開するかどうかを選べる
- 再開した試合は、中断前と同じスコア・ターン・局面・ボール位置・選手配置・陣形・方式で続行できる
- 再開は中断した時点の画面から行う（手の選択中なら試合画面、方式の選び直し中なら方式の選び直し画面、ハーフタイム中ならハーフタイム画面）

#### FR-15 設定

- BGM 音量・効果音音量をそれぞれ変更できる
- ヒント表示（FR-19）の ON/OFF を切り替えられる。初期値は ON
- 変更した設定はアプリ再起動後も保持される

#### FR-16 噛み合わせ表示

- 試合画面のピッチ上で、30エリアそれぞれについて両チームの現在の人数と、数的優位・同数・不利の区別を表示する
- 表示は、方式による動き方・プレスで寄せた選手を反映した現在の配置に基づく
- 相手の現在の陣形・方式を常に表示する
- 優位・同数・不利は、色だけでなく記号や数値でも区別できる（色覚に依存しない）
  - 試合の作戦ボードでは、形の違う駒（自分 ●・相手 ◆）の数で区別する（記号を全エリアに出すと盤面の情報が多すぎたため。2026-10-22。`functional-overview.md`「表示仕様」）
- 表示される人数は、ターン判定（FR-05）で用いる値と一致する

#### FR-17 戦術の解説

- 提供するすべてのフォーメーションと方式について、特徴・得意な攻め方・弱点の解説がある
- 試合開始時・得失点後・ハーフタイムの選択画面から、解説を参照できる
- 解説は、FR-02・FR-20 で定めた噛み合わせと動き方に矛盾しない
- 相手との組み合わせに応じた解説は、組み合わせごとに手書きしない。フォーメーションラボから移植する「特徴タグ × 噛み合わせルール」から導出する（陣形・方式を追加しても、組み合わせ数に比例して執筆量が増えないようにするため）
- 解説の各記述は、戦術原則カタログ（`functional-overview.md`）の原則に紐づく

#### FR-18 試合後の振り返り

- 試合結果画面から振り返りを開ける
- エリア別に、判定の勝ち数・負け数を集計して表示する
- 局面別（攻撃・ネガティブトランジション・守備・ポジティブトランジション）に、判定の勝ち数・負け数を集計して表示する
- 各得点・失点について、そこに至るまでの直前数ターンの選択・選手の動き・判定理由を表示する（表示ターン数は `functional-overview.md` で定める）
- 時間帯ごとの両者の陣形・方式と、その噛み合わせを表示する

#### FR-19 ヒント表示

- ヒント表示が ON のとき、行動選択時に選択肢ごとの判断材料（そのエリアの現在の人数差・背後のカバーの有無など）を表示する
- ヒントは判断材料を示すだけで、「最善の選択」を指示しない（読み合いの余地を残す）
- ヒント表示が OFF のときは表示しない

#### FR-20 守備方式・攻撃方式

- 守備方式としてゾーンディフェンス・マンツーマンディフェンスを、攻撃方式として保持型・カウンター型を選べる
- 方式は選手の動き方を規定する。守備方式はボールを持っていないときの動き方を、攻撃方式はボールを持っているときの配置とトランジションでの振る舞いを決める
  - ゾーン: ボールサイドへスライドし、ボール周辺を圧縮する（逆サイドが薄くなる）
  - マンツーマン: 自陣・中盤の相手に同じエリアでマークをつけ、余った選手は自陣中央でカバーにつく
  - 保持型: 幅と高さを取り、敵陣に人数をかける（自陣が薄くなる）
  - カウンター型: 基本配置で構え、奪った直後にカウンターを選んだ瞬間に前線へ人が飛び出す
- 各方式の具体的な動き方の規則の正本は `functional-overview.md`「アルゴリズム設計」とする
- 各方式の動き方は、戦術原則カタログの原則に紐づく

#### FR-21 試合中の方式変更

- 得失点後のキックオフ前に、両者が守備方式・攻撃方式を同時・秘匿で選び直せる。ただしハーフの最終ターンの得点では選び直しを行わない（直後のハーフタイムで陣形と方式を選び直せるため。試合結果へ進む場合も行わない）
- 選び直した方式は、キックオフ時に両者同時に開示される
- 上記とハーフタイム（FR-08）以外のタイミングでは方式を変更できない（方式が毎ターンの手と区別できなくなるため）
- 相手の現在の方式は、試合中つねに表示される（FR-16）

#### FR-22 理解度チェック

- タイトル画面から理解度チェックを開ける
- 学習目標 LG-1〜4 のそれぞれに対応した場面問題を、各2問以上出題する
- 回答すると、正誤と、根拠となる人数・位置・原則の解説が表示される
- 学習目標ごとの正答状況を確認できる
- 結果は端末内にだけ保存し、外部へ送信しない
- 公開前プレイテストの学習効果の測定（§1.5）に使う8問（LG ごとに2問）は、本機能の出題セットの一部とする

#### FR-23 単純化の明示

- チュートリアルの最後に、このゲームが表現していること・していないこと（単純化カタログの全項目）を一覧で示す
- タイトル画面からも、同じ一覧をいつでも参照できる
- 解説・振り返り・ヒントで、単純化に関わる場面が出たときは「実戦ではこう」を一言添える
- 単純化カタログの正本は `functional-overview.md` とし、アプリ内の表示はカタログと一致する

#### FR-24 ターン結果の盤面での表示

- 手を選ぶのも、ターン結果を見せるのも、作戦ボードで行う。作戦ボードは、縦向きのピッチを斜めから見た半3Dの盤面とし、選手はチェスのような立体の駒で表す（利用者は上へ攻める）
- 両者の手の開示後、両チームの駒とボールが2拍で短く動く。1拍目は判定前の位置から判定時の位置へ（プレー）、2拍目は次のターン開始時の位置へ（詰め直し）。手で動いた選手だけでなく、方式（スライド・マークの追従など）で位置が変わった選手も動き、プレーの後にチーム全体がボールに合わせて組み直ることを見せる（2026-11-03 に2拍にした）。1拍目の終わりに、結果を盤面の動きで見せ（得点はゴールへ飛び込んでゴールが光る、セーブ・ボールを奪ったときは奪った場所に輪、オフサイドは旗、膠着はボールが跳ね返る）、同時に判定理由（何人対何人・カバーの有無）を表示する（2026-11-03 に、開示の瞬間から1拍目の後へ移した）
- 動く時間は設定値として外部化する（1試合10〜15分に収めるため。NFR-18）
- 動きはターン判定の結果（判定前の配置と、次のターン開始時の配置）から作る。判定と食い違う動きを見せない
- 駒の数は、各エリアの人数と一致する（エリア内の細かい位置関係はルールで扱わないため。単純化 SIM-06）
- 動いている間も、利用者は次のターンへ進める（待たせない）
- 低価格帯の Android 端末でも途切れずに動く（目標値は非機能要件定義書）

> **2026-10-23 に置き換えた**: 0.6 までの FR-24 は「ターン結果の3D演出」だった（開示後に3Dのピッチで選手が動く
> 5秒以内の演出を再生し、スキップできる）。作戦ボードの上で駒とボールを動かす表示を作った結果、盤面だけで
> どこで何人対何人だったかが読め、ゲームとして十分に面白いと判断した（プロダクトオーナー）。3D の舞台・カメラ・
> 演出の状態を作る量を、読み合いに直接効く盤面に回すため、3D 演出をやめた。番号は付け直さず、中身を置き換えた
> （以降の工程の追跡を切らないため）。

## 6. スコープ

### 6.1 対象範囲（MVP）

- 1人 vs CPU の試合（FR-01〜FR-11、FR-20、FR-21）
- ターン結果の盤面での表示（FR-24）
- チュートリアル・戦績・中断再開・設定（FR-12〜FR-15）
- 戦術学習（噛み合わせ表示・解説・振り返り・ヒント・理解度チェック）（FR-16〜FR-19、FR-22）
- 戦術的妥当性（単純化の明示）（FR-23）
- 戦術原則カタログ・単純化カタログ・セルフレビューのチェック観点の整備（§7 #14〜#15）
- 公開前プレイテストの実施（学習効果の測定と違和感の収集）
- 対象プラットフォーム: Android（スマートフォン・横向き）。PC の画面も横長のため、後続マイルストーンの Windows 版で画面の配置を作り直さずに済むよう、横向きだけで設計する（2026-10-18 決定）

### 6.3 リリース判定基準

一般公開は、次をすべて満たしたときに行う。

- すべての P0 の機能要件の受け入れ基準を満たす
- 非機能要件定義書のすべての目標を満たす（実測値を記録済みであること）
- 公開前プレイテストで学習効果を測定済みである（§1.5。目標に届かない場合の扱いは公開前に判断する）
- ストアへの申告（対象年齢・コンテンツレーティング・データの取り扱い）を済ませている（§7 #18）

P1 の機能は、公開時点で完成していれば含める。完成していなければ公開後のアップデートで追加し、公開の
可否には影響させない。
