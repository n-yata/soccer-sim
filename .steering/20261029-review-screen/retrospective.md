## 計画と実績の差分

**計画と異なった点**:
- ミニピッチの2チーム表示は、はじめ「●2 ◆1」の形で作った。screen-common.md に「`1−0` が 24px で入る大きさ」とあったので、「自分−相手」の形に作り直した。**作る前に部品の表の決めごとを読む**べきだった。
- 集計の札「勝3 負1 膠1」は、ヒントの札と同じ 18px では奥の行のエリアに収まらなかった。エリアの幅に合わせて字を縮める形にし、下限は実測で 11px にした（12px では2桁×3の札が 0.1px はみ出した）。
- 得点のカードの列は、詳細設計の 560px では右の文が折り返しすぎた。400px にし、詳細設計も直した。
- 変換は、設計の `MatchController.review()` の中ではなく、`ViewConverter.review` に置いた（ほかの値の変換と同じ場所に置くため）。

**新たに必要になったタスク**:
- `ScreenHeader.add_to_right`。ヘッダーの右側にタブを置く口が無かった。はじめ `_ready` でタブを入れていたため、木に入らずに解放された画面（シーンの全件確認のテスト）でタブが孤立ノードになった。ノードの道筋で行を引き、組み立てるときに入れる形にした。
- `main_shell_test` の直し。「まだ作っていない画面」の例に S-07 を使っていた。
- スクリーンショットで見つけた3点の直し。①タブが縮められて1つずつしか見えない（`clip_tabs = false`）、②得失点の文が狭い、③凡例の記号が灰色で、棒の色と結び付かない。
- 実装検証を受けての分割。`ReviewPhasePage`・`ReviewGoalsPage` に分け、子を消す処理を `MatchScreenLayout.clear` に置いた。

## 学んだこと

**技術的な学び**:
- `TabBar` は既定でタブを縮める（`clip_tabs`）。ヘッダーのように幅を取り合う場所では、4つでも1つずつしか見えない。
- `@onready` の変数を使うメソッドは、画面をコードで組み立てる途中（`_init`。まだ木に入っていない）では使えない。そのため組み立てが `_ready` に分かれ、木に入らないまま解放されると、組み立て途中の部品が孤立ノードとして残った。木に入る前に呼ぶ口は、ノードの道筋で引く。
- GDScript の三項演算子では、`x if a as bool else y` は構文エラーになる。キャストは変数に分ける。
- gdUnit4 の文字列の判定は `starts_with`（`begins_with` ではない）。
- gdUnit4 は孤立ノードがあると、失敗0件でも終了コード 101 で終わる（tools/run-tests.sh は失敗として扱う）。

**プロセス上の改善点**:
- 変異は、集計のスイートだけを回して10個で約20秒に収まった（メモの「狙ったスイートだけ」が効いた）。
- スクリーンショットで、テストでは拾えない見た目の問題を3つ見つけた。画面の作業では、テストが通ったあとに必ず撮る。
- シェル経由で書き換えて `\` が化けた（14回目）。新しい作業の最初のテスト追記で、また Bash の Python を使った。テストの追記は Edit で行う。
- 並行セッションが同じ作業ツリーで動き、途中でコミットもした。こちらの変更は巻き込まれていなかった。`git status` と相手のコミットの `--stat` で確かめた。
