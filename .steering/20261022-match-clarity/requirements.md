# 要求内容

## 概要

PC で1試合を遊んだシャビから、次の3つの指摘があった。
- 盤面上の情報が多すぎて理解できない。
- ボールだけがマスに残り、コマが誰もいない状態が起きる。
- CPU の動きがランダムすぎて予測できない。

この3つを直し、「どのエリアで何人対何人だったから結果がこうなったか」を読み取れるようにする。あわせて、相手の手を読めるようにする。

## 背景

`0d1f42c` で試合画面（S-03）を作った。その受け入れ条件として、シャビが PC で1試合を遊んだ（2026-10-22）。調べた結果は次のとおり。

- **盤面**
  - 手を選ぶ時点で、次のものが同時に出ている。
    - 15エリアすべての角にある優劣記号。ほとんどが「＝」。
    - 背番号。
    - 選べる全エリアのヒントの札。プレスでは十数か所。
  - 結果の表示では、さらに次のものが重なる。
    - 方式の動きの長い点線の矢印。
    - 駒の上に重なる凡例。
  - 何を見ればよいかの優先順位が、画面に無い。
- **ボール**
  - これはコードのバグではない。仕様（functional-overview.md のアルゴリズム5〜7）の矛盾である。
  - CPU 同士で200試合（4800ターン）を自動で回すと、約7%（331ターン）のターンで、ボールのエリアに保持側の選手がいなかった。
  - **ドリブルが膠着したとき（160件）**: 運んだ選手は運ぶ先へ動いて固定される。けれど、ボールは元のエリアに残る。
  - **トランジションの後の配置区間のリセット（約110件）**: 選手は基本の位置に戻るが、ボールは奪った場所や運ぶ先に残る。
  - 残りは、そのあと膠着が続いて空のままになった分。
- **CPU**
  - 選べる手は平均13.5通りある。いちばん確率の高い手でも、平均26%しか選ばれない。
  - 評価値が最高の手を選んだのは53%だけだった。いまの設定値は τ=1.0、floor=0.1。
  - CPU の方式（守備方式・攻撃方式）と、選ぶ手が結びついていない。そのため、相手の方式を見ても何をしてくるかが読めない。

2026-10-22 にシャビと次のとおり決めた。
- **ボール**: 「保持者を置く」。
- **CPU**: 「方式の癖＋ブレを減らす」。
- **盤面**: モックの「シンプル案」で進める。センターサークルとペナルティエリアは残す。

## 実装対象の機能

### 1. 盤面を絞る（シンプル案）

正本の `TacticsBoard` の描き方を、次のように変える。

**消すもの**
- 角の優劣記号（▲・＝・▼）。
- 駒の背番号。駒は番号の無い ●（自分）・◆（相手）にする。
- 方式の動き（スライド・マーク・保持型の前進・リトリート）の矢印。
- 動きの凡例。

**残すもの・変えるもの**
- センターサークル・ペナルティエリア・ゴール・ハーフウェイラインの白線は残す。
- **駒**: エリアの中で、自分は左、相手は右に寄せて、1列に並べる。人数が多くてエリアに入らないときの扱いは、設計で決める。
- **ヒントの札**
  - 選べるエリアにだけ、エリアの下端に出す。
  - 差がある札（`+1`・`−1`）は目立つ色にする。
  - 差が ±0 の札（`±0`・`±0 GK` など）は控えめな色にする。
- **レーン名**: 左上に小さく出す。
- **ボール**: エリアの中の上側に描き、ボールのあるエリアを薄く明るくする。
- **矢印**: 次の2つだけにする。
  - 動きの矢印は、ドリブル・寄せ（プレス）・カバーだけ。
  - 選んだ手の矢印（ボールから運ぶ先）。

**仕様書の更新**
- 次の仕様書の記述を、上の形に直す。
  - functional-overview.md「表示仕様」のエリアの人数・優劣記号・選手の動き。
  - screen-design.md の S-03 の画面項目。
  - screen-03-match.md・screen-common.md の TacticsBoard。
  - component-design.md のうち該当する記述。
- 優劣（優位・同数・不利）は、エリアの中の ● と ◆ の数で読み取る。形で区別するので、色に頼らない（FR-16・NFR-20 は満たしたまま）。

### 2. ボールのあるエリアに必ず保持者を置く

ドメインのルールを変える。

**ドリブルの膠着**
- アルゴリズム5の攻守ターンで、ドリブルの結果が `STALL` のとき、運んだ選手を判定前のエリアに戻す。
- このとき、選手の固定の状態も判定前に戻す。ボールは元のエリアに残るので、ボールと運んだ選手が離れない。
- 判定（比較エリアの人数・カバー）は、いまと同じく「ドリブルで動いた後の配置」で行う。戻すのは、判定の後に次のターンへ持ち越す配置だけ。

**保持者を置く**
- 各ターンの開始時（キックオフ・攻守ターン・トランジションターン）に、ボールのエリアに保持側の選手がいなければ、ボールにいちばん近い保持側の選手を1人、ボールのエリアに置いて固定する。
- 対象には、配置区間のリセットの後と、得点・ハーフタイムの後のキックオフを含む。
- 「いちばん近い」の測り方と、同じ距離のときの順は、既存の規則に合わせて設計で決める。既存の規則は、ゾーン差＋レーン差と、配置の選手の順。
- 置いた選手の動きは、ターン記録の動き（Movement）に残す。こうすると、振り返りと 3D 演出で、ボールのところへ寄った選手として描ける。理由の値を足すかは設計で決める。

**仕様書の更新**
- functional-overview.md のアルゴリズム2・5・6・7に、この規則とエッジケースを書き足す。

### 3. CPU に方式ごとの癖を持たせ、ブレを減らす

アルゴリズム8を変える。

**方式の癖**
- CPU の方式ごとに「好む手」を決め、評価値に加点する。
- 加点の値は設定値（`cpu_config.tres`）にする（NFR-16）。
- 「好む手」の初期案は次のとおり。確定は設計で行う。

  | CPU の方式 | 好む手 |
  |---|---|
  | 攻撃方式 カウンター型 | 背後へのロングボール、前へのドリブル、トランジションのカウンター |
  | 攻撃方式 保持型 | ショートパス、サイドチェンジ、トランジションの保持 |
  | 守備方式 マンツーマン | プレス、即時奪回 |
  | 守備方式 ゾーン | カバー、リトリート |

**ブレを減らす**
- τ と floor の初期値を下げ、評価値の高い手に寄せる。値は、自動の試合で次の指標を測って決める。
  - 評価値が最高の手を選ぶ割合。
  - 方式ごとの、好む手の選択率。
- **変えないもの**
  - どの選べる手にも、確率が残ること（floor > 0）。
  - 利用者の手を参照しないこと。
  - 選べない手を選ばないこと（FR-11）。
- **仕様書の更新**: functional-overview.md のアルゴリズム8と、設定値の一覧に書き足す。

## 受け入れ条件

### 全体
- [ ] テストは先に失敗する状態から書く（Red→Green）。
- [ ] `tools/run-tests.sh` で次を確かめる。
  - 実行件数が0件でない。
  - 失敗が0件で、終了コードが0。
  - 型の警告（エラー扱い）が0件。
- [ ] 重要なテストが効いていることを、変異で確かめる。

### 盤面を絞る
- [ ] 盤面に、角の優劣記号・背番号・方式の動きの矢印・凡例が描かれない。
  - テストでは、描くかどうかを決める値で確かめる。例: 描く動きの数が、ドリブル・プレス・カバーの数と一致する。
- [ ] ヒントの札は、選べるエリアにだけ出る。差が ±0 の札と、それ以外の札で、見た目（色）が分かれる。
- [ ] 各エリアの ● と ◆ の数が、`BoardSnapshot` の人数と一致する（FR-16）。人数がエリアに入りきらないときも、人数を読み取れる。
- [ ] センターサークル・ペナルティエリア・ゴール・ハーフウェイラインが描かれる。
- [ ] スクリーンショットで、攻撃・守備（プレス）・結果の3場面を確かめる。文字や駒が重ならないこと、はみ出さないこと。
- [ ] 仕様書（表示仕様・画面設計・詳細設計）が、上の表示と一致する。

### ボールのあるエリアに必ず保持者を置く
- [ ] ドリブルが膠着した後のターン開始時、運んだ選手が判定前のエリアにいて、ボールと同じエリアにいる。
- [ ] ドリブルの膠着でも、判定に使う人数は、ドリブルで動いた後の配置の値のまま。いまの判定のテストは通ったまま。
- [ ] ボールのエリアに保持側がいない局面（トランジション後のリセット・ドリブルの膠着・SAVE）から、ボールにいちばん近い保持側の選手が1人、ボールのエリアに置かれ、固定される。同じ距離のときの順もテストで固定する。
- [ ] 固定シードの CPU 同士の試合を複数回し、すべてのターン開始時に、ボールのエリアに保持側の選手が1人以上いる（いまは約7%のターンで破れている）。
- [ ] 置いた選手の動きが、ターン記録に残る。

### CPU に方式ごとの癖を持たせ、ブレを減らす
- [ ] 好む手には、方式に応じた加点が入る。加点の値を設定で変えると、選択確率が変わる（NFR-16）。
- [ ] どの選べる手にも `floor / N` 以上の確率が残る。選べない手は選ばない。利用者の手を参照しない（既存のテストを保つ）。
- [ ] 固定シードの CPU 同士の試合を回して、次を確かめる。
  - 評価値が最高の手を選ぶ割合が、いまの 53% より上がる。目標値は設計で決める。
  - 方式ごとに、好む手の選択率が、ほかの方式のときより高い。
- [ ] 設定値の範囲の検査（`ConfigRepository`）に、加点の値が含まれる。

### PC での確認
- [ ] シャビが PC で1試合を遊び、次を確かめる。
  - 盤面が読み取れる。
  - ボールのところに必ず選手がいる。
  - CPU の方式から、手の傾向を読める。

## 成功指標

- シャビが盤面を見て、「どのエリアで何人対何人か」をすぐ読み取れる。
- CPU 同士の試合で、ボールのエリアに保持側がいないターンが 0%（いまは約7%）。
- 評価値が最高の手を選ぶ割合が 53% より上がる。そのうえで、方式ごとに手の傾向の差が出る。
- 相手の方式を見て、次の手の傾向を予想できる（シャビの体感）。

## スコープ外

以下はこのフェーズでは実装しません:

- 表示の「シンプル／詳細」の切り替え。
- ヒントの ON/OFF の設定画面。
- 3D 演出、試合中のメニュー、保存。
- CPU の強さの段階（強さは1種類のまま。FR-11）。
- CPU が得点後に方式を選び直すときの選び方（一様ランダムのまま）。
- 方式の解説文（アルゴリズム9）への癖の記述。
- ミニピッチ（S-02・S-05）の表示の変更。
