# 振り返り: スルーパスの運ぶ先へ守備が入ってきたら奪われる（2026-10-28）

## やったこと
- `OpenPlayJudge.through_pass_outcome` に「守備が運ぶ先へ入ってきた」を足した。プレスの寄せ・カバーの下がり・マークの追従のどれでも、読みに関係なく LOSS。判定は判定の動き（守備の手・攻撃の手・付け直し）から `defender_entered` で出す。
- 判定理由（「相手に入られて」／「運ぶ先に入って」）とスルーパスの説明の文を直した。
- コミット前レビューの Medium を受けて、ヒントの札に「マーク注意」を足した（相手が何もしなくてもマーカーがついてくる運ぶ先。判定と同じ `defender_entered` を、ヒントの攻撃の手の動きに掛ける）。

## 数字（壊れていないかの目安）
- CPU 同士: 1試合の点 2.53、入れ替わり 5.5、スルーパスの選択率 12%、ロスト 7% → 47%（マークの追従を除くと 8%）。シャビの判断でこのまま遊んでみる。

## 確かめ方
- 全体のテスト 650件・失敗0。
- 変異: 判定 5個のうち4個 KILLED（残る1個は等価。守備側だけを数える条件は、スルーパスで攻撃側が動くのは受け手の運ぶ先への走り込みだけで、列の数が偶数なので運ぶ先と守備側の視点の運ぶ先が一致しないため。理由は `defender_entered` のコメントに残した）。札 5個は5個とも KILLED。

## うまくいったこと
- 判定とヒントで同じ関数を使ったので、札と結果が食い違わない。
- 既存の画面のテスト（スルーパスの札の色）が、キックオフのマンツーマンの場面で「マーク注意」を拾って落ち、ヒントの変化が画面まで届くことを確かめられた。

## 次に気をつけること
- 判定の規則を変えたときは、ヒントの札（判断材料）が新しい規則とずれないかを、レビューの前に自分で見る。今回はレビューで初めて気づいた。
- ロスト 47% はマークの追従が主な理由。シャビが遊んで強すぎ・弱すぎを判断する。

## 申し送り
- 「入ってきてまた出ていった」守備も入ってきたと数える（今の付け直しの規則では起きる経路が見つかっていない）。
- CPU の評価は「マーク注意」を使っていない（今の CPU の点数には影響しない。強すぎると感じたら評価に入れる）。
