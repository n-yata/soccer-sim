# 要求内容

## 概要

試合の点の入り方と攻守の入れ替わりを見直す。

- 狙う形: 1試合（前後半 24 ターン）で 2〜3点。攻守がこまめに入れ替わる。
- 直し方は2つ。
  1. **守備がボールを奪いやすくする**（判定のルール）。
  2. **CPU がゴールを狙うようにする**（CPU の評価値）。
- シュートの条件とターン数は変えない。

## 背景

前の作業から、「点が入りにくい」が申し送りになっていた。2026-10-23 に、CPU 同士の試合を一時スクリプトで 200 試合回して測った（固定シード）。

| 測ったもの | CPU 同士 | 利用者が前へ運ぶ手のとき（テストの補助の forward_choice） |
|---|---|---|
| 1試合の点数 | 0.34点（0-0 が 77%） | 0.66点（利用者は 0.16点） |
| 1試合の攻守の入れ替わり | 2.8回（1回の保持は平均 8.6ターン、最長 23ターン） | 3.5回（平均 6.8ターン） |
| シュート | 0.38本／試合（決まる割合 89%） | 利用者は 0.22本／試合 |
| 攻守ターンでボールを失う割合 | 自陣 2%・中盤 3%・敵陣 4% | 中盤 7% |

分かったこと:
1. **攻守がほとんど入れ替わらない**
   - パスとドリブルの9割前後が通り、ボールを失うのは数%しかない。
   - 片方のチームが、ほぼ1ハーフずっとボールを持つ試合が多い。利用者が守備側になると、10ターン以上ずっと守るだけになる。
2. **CPU がシュートを打たない**
   - CPU の評価値は「運ぶ先での人数差」だけで、ゴールへの近さとシュートの価値を見ていない。
   - 守備が固い敵陣でのシュートより、空いたエリアへのパスを選ぶ。打てば9割決まるのに、1試合 0.4本しか打たない。
3. **利用者が前へ運んでも点になりにくい**
   - 中盤で膠着しやすい。敵陣では守備が多く、シュートの条件（人数で上回る）を満たしにくい。

シャビと決めたこと（2026-10-23）:
- 目標の点数: **2〜3点**。
- 攻守の入れ替わり: **よく入れ替わる**（1回の保持が 2〜4ターン、1試合で 6〜10回）。
- 直し方: **守備が奪いやすく**、**CPU がゴールを狙う**。
  - シュートの条件をゆるめる案と、ターン数を変える案は採らない。

## 実装対象の機能

### 1. 守備がボールを奪いやすくする（判定のルール）
- 攻守ターンの判定（アルゴリズム5）を見直し、守備の手が当たったとき（相手が来ると読んだエリアに実際に来た）や、同数のときに、守備がボールを奪える場面を増やす。
- 具体的な規則は、設計で案を比べて決める。候補:
  - 同数でカバーがあるときは、膠着ではなく奪取にする。
  - 守備が読みを当てた（制限したエリアが運ぶ先と同じ）ときに、同数でも奪取にする。
  - 膠着が続いたら（例: 2回）、ボールを失う。
- 「読み合い（相手がどこへ来るかを読む）が報われる」ことを保つ。読みを当てた守備が得をする形を優先する。
- トランジション（アルゴリズム6）は、入れ替わりが増えたときの影響を見て、必要なら合わせて見直す。

### 2. CPU がゴールを狙う（CPU の評価値）
- CPU の手の評価値（アルゴリズム8）に、次を足す。
  - ゴールへの近さ（前へ運ぶ手ほど高い）。
  - シュートの価値。
- 足し方の重みは、設定ファイル（`cpu_config.tres`）の調整値にする。
- 利用者に見せるヒント（FR-19）の人数差は変えない（CPU の評価値だけを変える）。

### 3. 計測の仕組み
- 点数・攻守の入れ替わり・シュートの数を、決まった試合数と固定シードで測る計測を、テストとして持つ。
  - 一時スクリプトではなく、リポジトリに残す（調整のたびに同じ物差しで測るため）。
- 利用者の遊び方を模した手（例: CPU と同じ評価で、温度を下げて最善手を選びやすくした手）でも測る。CPU 同士だけでは、利用者が点を取れるかが分からないため。

## 受け入れ条件

- [ ] 固定シードの計測（CPU 同士。試合数は設計で決める）で、次を満たす。
  - 1試合の点数の平均が 2〜3点。
  - 1試合の攻守の入れ替わりが 6〜10回（1回の保持の平均が 2〜4ターン）。
- [ ] 利用者の遊び方を模した手でも、利用者の側に 1試合 1点前後の得点がある（一方的に取れない・取られないことを、測った値で確かめる）。
- [ ] 守備の手が当たったときに奪える規則が、判定の例（`functional-overview.md` の判定例）とテストで固定されている。
- [ ] 読みを当てた守備が得をする（当てたときのボールを奪う割合が、外したときより高い）ことを、計測で確かめる。
- [ ] CPU の評価値の追加の重みは `cpu_config.tres` にあり、範囲外の値は初期値に戻る（既存の設定の検査と同じ方針）。
- [ ] ヒント（FR-19）の値は変わらない（既存のヒントのテストがそのまま通る）。
- [ ] ルールの変更に合わせて、仕様書を更新する。
  - 機能概要のアルゴリズム5・8。
  - 判定例。
  - 設定値の表。
  - 単純化カタログ（該当があれば）。
- [ ] 1試合の所要時間（NFR-18）に影響しないこと。ターン数は変えないので、時間は変わらない想定。
- [ ] シャビが PC で1試合を遊び、点の取り合いと攻守の入れ替わりを楽しめる。

## 成功指標

- 毎試合、どちらかに点が入り、0-0 が少なくなる。
- 利用者が攻めも守りも、こまめに遊べる。
- 守備の読みを当てたときに、ボールを奪える手ごたえがある。

## スコープ外

以下はこのフェーズでは実装しません:

- シュートの条件（シュートできるエリア・決まる人数の条件）の変更。
- 1ハーフのターン数の変更。
- 陣形・方式の追加や変更。
- 案 C（ゾーンでもプレス・カバーの後に全員が詰め直すルール）。
- 画面の変更（判定理由の文言は、ルールの変更に合わせて必要なら直す）。

## 未決事項

- 守備が奪いやすくなる規則の具体（上の候補から、計測で比べて決める）。
- CPU の評価値の足し方（ゴールへの近さの重み・シュートの価値）と初期値。
- 計測の試合数と、テストとしての置き場所・実行時間。全体のテストの時間（いま約3分）を大きく延ばさないこと。
- 利用者の遊び方を模した手の定義。
- 自己対戦の検証（NFR-05〜07。先攻・後攻、方式の組み合わせの偏り）への影響の確かめ方。
