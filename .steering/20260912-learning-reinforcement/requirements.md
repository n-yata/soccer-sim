# 要求内容 — 学習体験の強化（FR-11 / FR-12 / FR-13）

- 作業日: 2026-09-12
- ブランチ: `feature/learning-reinforcement`
- 起点: シャビからの「このアプリをよりよくするアイデア」提案のうち、KPI に直結する3件を採用

## 背景

`requirements-definition.md` §1.4 のプライマリ KPI は
**「MVPで提供するフォーメーションについて、それぞれの基本的な特徴（強み・弱み）を
自分の言葉で説明できる状態になること」**である。

現状のアプリは FR-01〜FR-10 まで実装され「見る・読む」体験は揃っているが、
**KPI を満たしたかどうかを利用者が確認する手段がない**。具体的には次の3つが欠けている。

1. **理解度を確かめる手段がない** — 読んで分かった気になっても、説明できるかは別。
   アプリ側に「答えさせる」場面が一つもない
2. **1周したかが分からない** — KPI の達成条件は「全フォーメーションを1周確認し終えた時点」
   だが、どの組み合わせを見たかは利用者の記憶にしか残らない
3. **用語集への導線が読解の流れから切れている** — FR-10 で用語集画面は用意したが、
   解説文を読んでいる最中に分からない用語が出てきたとき、画面を離れて用語集へ行き、
   探して、戻ってくる必要がある。NFR-02（解説文の平易さ）の実効性が導線で目減りしている

## 追加する機能要件

### FR-11 解説文の用語インライン表示

解説文中に登場する登録済みサッカー用語を、その場で意味を確認できるようにする。

**受け入れ基準**:
- 比較画面の優位ポイント・総合判定理由に含まれる `soccerTerms` の用語が、
  本文中で他のテキストと区別できる表示になっている
- 用語を選択すると、その場に説明（`description`）が表示される
- 表示された説明は、再度の選択・他の用語の選択・`Escape` キー・本文外の選択のいずれでも閉じられる
- キーボードのみで用語の選択・説明の開閉ができる
- 複数の用語が部分的に重なる場合（例:「最終ライン」と「ライン間」）、
  **より長い用語が優先して一致する**（短い用語が長い用語の内部で誤って切り出されない）
- 用語が1つも含まれない解説文は、従来どおりの平文として表示される
- 用語集画面（FR-10）への導線は撤去しない。インライン表示は一覧性の代替にならないため併存させる

**スコープ外**: 一覧画面のフォーメーションカード内の説明文には適用しない。
カード全体が `role="button"` の操作要素であり、その内部に別の操作要素（用語ボタン）を
入れ子にすると、支援技術での読み上げと操作が破綻するため。

### FR-12 理解度チェック（クイズモード）

既存の静的データを出題データとして、理解度を確認できるクイズ画面を提供する。

**受け入れ基準**:
- 専用画面（`/quiz`）を持ち、一覧画面から遷移できる
- 次の3種類の設問を出題する（いずれも既存データから生成し、新たな解説文の執筆を要しない）
  1. **優劣判定**: 2つのフォーメーション名を示し「どちらが優位か」を
     「Aが優位 / Bが優位 / 互角」の3択で問う（正解は `Matchup.overallEdge`）
  2. **陣形識別**: ミニピッチ図のみを示し「これはどのフォーメーションか」を
     フォーメーション名の4択で問う（正解は `Formation.id`）
  3. **優位ポイント帰属**: 優位ポイントの文を1つ示し「どちらのフォーメーションのものか」を
     2択で問う（正解は `advantagesForA` / `advantagesForB` のどちら由来か）
- 回答すると即座に正誤が表示され、あわせて根拠となる解説
  （`overallReason` 等、既存データの文言）が表示される
- 全問終了後に正答数が表示され、もう一度挑戦できる
- 出題順・選択肢の並びはランダムだが、**乱数源を差し替え可能な形で実装し、
  テストでは決定的に検証できる**こと（`Math.random` を生成ロジックへ直接埋め込まない）
- 出題データが不足していて設問を作れない場合（フォーメーションが少ない等）、
  クラッシュせず「出題できない」旨を表示する

**スコープ外**: 成績の長期保存・難易度調整・制限時間。

### FR-13 学習進捗トラッキング

どの組み合わせを既に確認したかを記録し、可視化する。

**受け入れ基準**:
- 比較画面を表示した組み合わせを「確認済み」として記録する
- 記録は**フォーメーションの順序に依存しない**（`A vs B` と `B vs A` は同一の組み合わせ）
- 相性マトリクス画面のセルで、確認済み／未確認が視覚的に区別できる
- 進捗（確認済み件数 / 全組み合わせ件数）が数値で確認できる
- 進捗を消去する手段がある
- 記録はブラウザの `localStorage` に保存し、再訪時に復元される
- **`localStorage` が利用できない環境（プライベートモード・無効化・容量超過）でも
  アプリが壊れない。** 記録できないだけで、他の機能は従来どおり動作する
- **保存データが壊れている・改竄されている場合に、それを信用して描画しない。**
  読み込み時に形式を検証し、不正なら空の状態として扱う

**スコープ外**: 複数端末間での同期（バックエンドを持たないため）。

## 非機能要件との関係

| NFR | 本作業での扱い |
|---|---|
| NFR-01 ユーザビリティ（3クリック以内） | FR-12・FR-13 の導線は一覧画面から1クリック。既存の比較導線のクリック数は増やさない |
| NFR-02 解説文の平易さ | FR-11 が直接寄与する。クイズの設問文・解説文も既存データの文言を流用し、新たな専門用語を持ち込まない |
| NFR-03 フォーメーション追加の容易さ | FR-12 の出題・FR-13 の全組み合わせ件数は `formations` / `matchups` から算出し、データ追加のみで追随すること（設問数・分母のハードコード禁止） |

## 制約・前提

- バックエンド・DB を持たない構成は維持する（`requirements-definition.md` §7 制約3）
- 新規の外部依存パッケージを追加しない（クイズ・ポップオーバーとも自前実装で足りる）
- 既存の FR-01〜FR-10 の挙動を変更しない（FR-11 は表示の追加、FR-13 は記録の追加）
