# 要求内容

## 概要

フォーメーションを4種追加する（5-3-2 / 4-1-4-1 / 3-4-3 / 4-4-2ダイヤ）。
あわせて、追加形の特徴を表現するための特徴タグと噛み合わせルールを補う。
フォーメーションは4種→8種、組み合わせは6組→**28組**になる。

## 背景

A-1（`.steering/20260912-matchup-generation/`）でマッチアップ解説をタグ＋ルールからの
導出へ置き換えた。本作業はその**答え合わせ**であり、「フォーメーション追加がデータ追加のみで
済むか」を実地で検証する段として分離していた。

### 着手前の実測結果（重要）

追加予定の4種をドラフトとして作り、既存の `deriveTags` に通してタグを導出し、
既存ルール表で何件発火するかを実測した。結果は以下。

| 追加形 | 導出されたタグ | 評価 |
|---|---|---|
| **5-3-2** | `2トップ` `中盤3枚` | **最終ラインのタグが付かない**（DF5人は `3バック`/`4バック` のどちらでもない） |
| **4-4-2ダイヤ** | `4バック` `2トップ` | **中盤の菱形が表現できない**（フラットでないため `中盤フラット4枚` に当たらない） |
| 4-1-4-1 | `4バック` `1トップ` `中盤実質5枚` | おおむね機能する |
| 3-4-3 | `3バック` `3トップ` `ウイング有` `ウイングバック有` `中盤フラット4枚` | よく機能する |

**新規が絡む22組のうち9組で、片側のルール発火が0件**になり、解説が `stats` 由来の汎用
フォールバック文に落ちる。最悪は **4-4-2 vs 4-4-2ダイヤ で両サイド0件**（噛み合わせの解説が
一切出ず、総合判定も自動的に「互角」になる）。9組のうち7組は 5-3-2 が絡む。

**結論: A-1 の抽象化は「既存の形のバリエーション」は覆えるが、「構造的に新しい形」
（5バック・菱形の中盤）は覆えていない。本作業はデータ追加のみでは完了しない。**

ただし A-1 の成果が無駄になったわけではない。必要なのは新タグ2〜3個と新ルール数本であり、
コストは「新タグ × 既存タグ」のオーダーに収まる。手書き時代なら28組すべての解説文を
執筆する必要があった。

### 副産物

3-4-3 を追加すると「`中盤フラット4枚` を持ち、かつ `4バック` ではない」形が生まれ、
A-1 で「現行データでは到達不能」として許容リストに入れた **R11 が到達可能になる**。
許容リストから外せる。

## 実装対象の機能

### 1. 特徴タグの追加（`src/types/formation.ts` / `src/data/formationTags.ts`）

- `5バック`: 最終ラインが5人の形を表現する
- `中盤ダイヤ`: 中盤4人が菱形（フラットでない）に並ぶ形を表現する
- `アンカー1枚`: 中盤の底に1人だけを置く形を表現する

**既存4種のタグは1つも変わらないこと**（変わると校正アンカーが動く）。

### 2. 噛み合わせルールの追加（`src/data/matchupRules.ts`）

実測で判明した「片側0件」の9組を埋める。5バック側・5バックの相手側・中盤ダイヤ側・
アンカー1枚の相手側の噛み合わせを補う。

### 3. フォーメーションの追加（`src/data/formations.ts`）

5-3-2 / 4-1-4-1 / 3-4-3 / 4-4-2ダイヤ の4種を、選手配置・特性スコア・説明文とともに追加する。

## 受け入れ条件

### タグの追加
- [ ] 追加3タグが設計どおりの条件で導出される（境界値を含む）
- [ ] **既存4種（4-4-2 / 4-3-3 / 4-2-3-1 / 3-5-2）の導出タグが1つも変わらない**
- [ ] 追加4種が設計どおりのタグを持つ

### ルールの追加
- [ ] **28組すべてについて、両サイドに1件以上の「ルール由来の」優位ポイントが出る**
      （フォールバック文に頼る組が0になる）
- [ ] テーマをまたいだ条件の包含が発生していない（既存テストが検知する）
- [ ] 採用されないルールが無い（許容リストから `R11` を外し、新規の到達不能ルールも作らない）

### フォーメーションの追加
- [ ] 一覧・比較・マトリクス・クイズの各画面が8種／28組で破綻なく動作する
- [ ] **A-1 の校正アンカー6件（既存4種の判定）が変わらない**
- [ ] **用語集18件すべてが、生成後のマッチアップ文言に登場する**
      （A-1 の振り返りの申し送り。ルール表段階の検査は死んだルールでも緑になる）
- [ ] `npm test` / `lint` / `typecheck` / `build` がすべて成功する
- [ ] `.vue` ファイルの変更が無い（NFR-03: データ追加のみで画面が拡張される）

### コンテンツ品質
- [ ] 追加4種の説明文・特性スコアが、一般的な戦術理論に照らして妥当
- [ ] 新規ルールの文言が初心者にも平易（NFR-02）で、未登録の専門用語を持ち込まない
- [ ] 28組の生成結果を目視し、極端な偏り（片側0〜1件に対し他方が5件以上）が無い
- [ ] `docs/content-review-checklist.md` に沿ってセルフレビューした

## 成功指標

- **定量**: フォールバックに頼る組が0、28組すべてでルール由来の解説が出る
- **定性**: A-1 の「データ追加のみ」という目標に対して、**実際に何が追加で必要だったか**が
  ドキュメントに記録され、次回（A-3 や更なる形の追加）の見積もりに使える状態になる

## スコープ外

- **A-3: 局面別の形**（保持時／非保持時）— `positions` の型変更を伴うため独立した作業とする
- 上書き機構（生成結果を個別に手書きで差し替える仕組み）— A-1 の判断を引き継いで作らない
- 画面（`.vue`）の変更 — データ追加のみで拡張される設計のため発生しない想定
- フォールバック文の撤去 — 28組で不要になっても、安全網として残す

## 既知のリスク

- **`MatrixPage.test.ts` が架空の追加フォーメーションとして id `4-1-4-1` を使っている。**
  実在の形として 4-1-4-1 を追加すると id が衝突する。実測して影響を確認し、問題があれば
  フィクスチャ側の id を架空のもの（例: `9-9-9`）へ変更する。
  「架空の追加を模す」意図のフィクスチャに実在 id を使うのは意図に反するため、
  この変更は「テストを通すための改変」には当たらない
- タグを3つ増やすとルールの組み合わせ空間が広がり、**テーマをまたぐ包含**や
  **タグの共起による重複発火**が新たに生まれやすくなる（A-1 で実害を出した経路）。
  既存の検知テストが効くが、新規ルールを足すたびに確認すること
