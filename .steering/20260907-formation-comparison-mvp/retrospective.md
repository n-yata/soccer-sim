## 計画と実績の差分

**計画と異なった点**:
- `npm install`直後の`npm audit`でesbuild関連の脆弱性（開発サーバー限定）を検出したため、
  design.mdで想定していた`vite@^5.4.0`を`npm audit fix --force`で`^6.4.3`に、連動して
  `vitest`も`^4.1.11`に更新した。
- `tsconfig.json`のパスエイリアス（`@/*`）設定漏れ、`jsdom`型定義の誤指定により
  `vue-tsc --noEmit`が最初失敗した。vite.config.tsのresolve.aliasだけでは
  TypeScriptコンパイラには伝わらないため、tsconfig側にも同じ設定が必要だった。
- ESLint/Prettierの初期セットアップが不十分（`typescript-eslint`プラグイン本体の
  未インストール、Prettier設定ファイル不在）だったことが`review-implementation`で
  指摘され、追加で整備した。
- `npm run format`（Prettier）を最初`prettier --write .`として実行した結果、
  `docs/`・`.steering/`・`AGENTS.md`等の**コミット済みファイルまで広範囲に整形してしまう
  事故**が発生した。`git checkout --`で復元し、`format`スクリプトを`src/**/*.{ts,vue}`に
  限定、`.prettierignore`でも二重に防御した。**フォーマッタや一括置換系のコマンドを
  新規導入するときは、必ず対象範囲を絞ってから初回実行することを徹底する必要がある。**

**新たに必要になったタスク**:
- `review-implementation`・`review-pre-commit`の指摘対応として、GKラベルの座標修正・
  マッチアップ全組み合わせの網羅テスト・ドメイン制約テスト・キーボード操作対応・
  グリッド可変化・ドキュメント間の矛盾解消などを追加で実施した。
- 同一フォーメーション同士のURL直打ちというエッジケース（`getFormationById`は成功するが
  `getMatchup`が`undefined`になる）への対応。これは元々の詳細設計で「マッチアップ未検出は

## 学んだこと

**技術的な学び**:
- Vue 3 + Viteのパスエイリアスは、`vite.config.ts`（実行時解決）と`tsconfig.json`
  （型チェック）の両方に同じ設定が必要。片方だけでは型チェックがすり抜けたり、
  逆に実行できるがビルドが通らなかったりする。
- `vi.hoisted`を使うと、テストケースごとに異なるモック状態（`vue-router`の`route.params`、
  データモジュールの内容）を安全に切り替えられる。`vi.mock`のホイスティングと組み合わせる
  典型パターンとして今後も使える。
- SVGのviewBox外描画は、実際に描画してみるまで気づきにくい欠陥。今回のようにテキスト
  要素のy座標を計算で決める場合、境界値（最小/最大の入力）でのはみ出しチェックを
  実装直後に機械的に行うべきだった（後の`review-implementation`で発覚）。

**プロセス上の改善点**:
- `review-implementation`と`review-pre-commit`を2段階で実施したことで、実装直後の
  品質問題（GKラベル等）と、コミット前の仕様整合性問題（同一フォーメーム同士のエラー処理、
  ドキュメントの矛盾）を役割分担して発見できた。両方を1回のレビューでまとめようとすると
  見落としが増えていた可能性がある。
- 一括置換・一括整形コマンド（`sed`, `prettier --write`）を実行する前に、対象範囲を
  必ず限定してから実行する習慣が必要。今回は`sed`は都度対象ファイルを明示していたため
  実害が無かったが、`prettier --write .`は無限定で実行してしまい、コミット済みファイルを
  広範囲に書き換える事故になった。

## 次回への改善提案

- 新しいツール（フォーマッタ、リンタ、一括変換スクリプト）を初めて実行するときは、
  まず`--dry-run`相当のオプションがあれば使う、無ければ対象を狭いスコープに限定してから
  試すことを徹底する。
- SVG等の座標計算を伴うコンポーネントを実装したら、その場で境界値（最小・最大の入力）を
  レンダリングして目視かテストで確認する工程を実装直後に組み込む。
- エラーハンドリングの「発生しない前提」とする設計判断は、URL直打ちのような正規UIを
  経由しない経路も含めて再確認してから記載する。今回は一覧画面のトグル操作だけを見て
  「同一フォーメーション同士は発生しない」と判断したが、比較画面のルートは独立してアクセス
  可能なため、URL経由の到達可能性を見落としていた。
