# 設計書

## アーキテクチャ概要

既存のVue画面・共通コンポーネントを改修する。比較計算と静的データは変更しない。画面固有の操作は各Pageに置き、横断する視覚表現だけを既存トークンと共通コンポーネントで揃える。

```
AppHeader / PageHeader / tokens.css
  ├─ FormationListPage → ComparisonPage
  ├─ MatrixPage ──────→ ComparisonPage
  ├─ GlossaryPage
  └─ QuizPage
```

## デザイン方針

- **主役**: 戦術ボードであるピッチ図と、その配置が生む結論。トップ画面はミニピッチを選ぶ体験、比較画面は大きなピッチを読み解く体験にする。
- **配色**: 既存の中立面・ブランド緑・A青/B赤を維持する。新しい意味色を増やさず、文字の階層と余白で視線を誘導する。
- **文字**: 既存のOS標準フォントとトークンを維持する。短い動詞を用いた操作文言と、読み物に適した行長を優先する。
- **レイアウト**: 共通の1200px外枠を維持し、画面内の本文に必要な幅だけを与える。主要情報を先に、設定・補助操作を後に置く。375pxで縦方向に自然に読める順序を基準にする。
- **動き**: 操作への応答のみ使い、自動で繰り返す装飾は増やさない。既存の軽減設定を維持する。

## コンポーネント設計

### AppHeader / PageHeader

- 現在地、各画面への導線、ページの目的を一貫して示す。
- 比較画面の現在地は、トップレベルの「一覧」への帰属が分かるようにする。
- 全画面共通の外枠と見出し階層を維持する。

### FormationListPage / FormationCard

- 選択数と選択した名前を操作の近くに表示する。選択カードの視覚状態とアクセシブルな状態を一致させる。
- 2件目で自動遷移する既存の流れを維持する。選択の取り消しはカードの再操作で行う。
- 外部リンクは主タスクの選択操作から離し、視覚的な優先順位を下げる。

### ComparisonPage

- 画面冒頭を「組み合わせ → 結論 → ピッチと凡例 → 理由」に整理する。
- A/B変更と表示オプションを独立した二次操作として置き、比較結果を遮らない。
- 特性チャート、優位ポイント、シミュレーションを見出しと短い説明で区切る。既存ロジックとイベントは維持する。

### MatrixPage

- 行・列の読み方を短く説明し、セル内で有利・互角・未定義を文字または記号でも示す。
- 表のヘッダーと行ラベルを狭い画面でも追えるようにし、横スクロールは表の領域内に限定する。
- 進捗の消去操作は学習の主要導線より弱く見せる。

### GlossaryPage

- 用語を見つけるための画面内検索を追加する。入力された文字が用語名または説明に含まれる項目を表示する。
- 検索結果がない場合は条件を変える案内と検索解除を示す。カテゴリ構成と既存用語データは維持する。

### QuizPage / QuizQuestionCard

- 問題番号と正解数の進捗を分かりやすく示し、回答後の正誤・解説・次の操作を連続して確認できるようにする。
- 最終結果は得点に加え、学習の次の行動（再挑戦・比較）を明確にする。採点・出題のロジックは維持する。

## データフロー

### 一覧から比較

1. 1件目のカードを選ぶと選択状態と名前を表示する。
2. 異なる2件目を選ぶと既存のルートで比較画面へ遷移する。
3. 比較画面はURLのA/Bと静的データから結果を表示する。

### 用語の検索

1. 入力文字を画面ローカルの状態に保持する。
2. `soccerTerms`から用語名または説明に部分一致する項目を絞る。
3. 結果が0件なら検索解除の操作を示す。データやURLは変更しない。

## エラーハンドリング戦略

比較URLに該当する組み合わせがない場合の既存エラー表示を維持する。用語検索の0件は正常な空状態として扱う。新しいエラークラスは設けない。

## テスト戦略

- 既存の各画面テストで操作・採点・画面遷移の回帰を確認する。
- 選択状態、用語検索の一致・不一致・空入力、マトリクスの非色情報、クイズの状態遷移について必要なテストを追加する。各テストは失敗を先に確認する。
- `npm test`、`npm run lint`、`npm run typecheck`、`npm run build`を実行する。
- 実ブラウザで全5画面を375px、768px、デスクトップ幅で確認し、主要操作・キーボード操作・コントラスト・操作領域を記録する。アプリ内Browserの接続が企画時点で利用できないため、接続を再確認する。

## 依存ライブラリ

追加しない。

## ディレクトリ構造

既存の`src/pages/`、`src/components/`、`src/styles/`内で改修する。作業記録は本ステアリングディレクトリに置く。

## 実装の順序

1. 現行5画面のソースと、可能になり次第実画面を確認する。
2. 共通表示と一覧・比較の主導線を調整する。
3. 相性表、用語集、クイズの学習導線を調整する。
4. テスト・実画面確認・実装レビュー・コミット前レビューを実施し、必要な永続ドキュメントと振り返りを更新する。

## セキュリティ考慮事項

- 用語検索は文字列比較のみとし、ユーザー入力をHTMLとして解釈しない。
- 外部リンクの既存の`rel="noopener noreferrer"`を維持する。
- URL、シークレット、アカウント情報のハードコードを追加しない。

## パフォーマンス考慮事項

用語数は少数の静的データなのでクライアント側のcomputedによる絞り込みで十分。画面表示を妨げる追加通信や依存ライブラリは導入しない。

## 将来の拡張性

見た目の共通性は既存トークンとコンポーネントに集約する。追加画面にも同じ見出し・操作階層を適用できる。
