# 要求内容

## 概要

毎ターンの手の選択を簡素化する。攻撃・守備はゲームが行き先を決めた手を最大4つのボタンから選ぶだけにし、
ポジトラ・ネガトラはボタン2つから選ぶだけにする。盤面でエリアを選ぶ手順を無くす。

## 背景

- 今は攻撃が6種類の手（ショートパス・ドリブル・スルーパス・ロングボール・サイドチェンジ・シュート）× 運ぶ先のエリア、
  守備が2種類の手（プレス・カバー）× 制限するエリアで、1ターンの選択肢が多すぎる。
- ポジトラのカウンターも運ぶ先を盤面で選ぶ2段階の操作になっている。
- 手の同時選択による読み合いがこのゲームの核なので、選択肢を減らしても読み合いは残す（自動進行にはしない）。

## 実装対象の機能

### 1. 攻撃の手（最大4つ）

手は距離の軸でそろえた3つと、ボールの位置で中身が変わる4つ目の枠。行き先は選ばない。

| 手 | 中身 | 出る条件 |
|---|---|---|
| ショートパス | 近くの味方へのパス。背後へ走り込める味方がいれば、短いスルーパス（今のスルーパス）になる | 行き先の候補が1つ以上ある |
| ロングパス | 遠くへのパス。今のロングボール（敵陣の奥へ）とサイドチェンジ（逆サイドへ） | 行き先の候補が1つ以上ある |
| ドリブル | ボールを持つ選手が運ぶ | 行き先の候補が1つ以上ある |
| 4つ目: シュート | その場で打つ（行き先なし） | ボールがペナルティエリア（敵陣ゴール前の列の L1・C・R1）にある |
| 4つ目: バックパス | ボールより後ろの味方へ戻す | ボールがペナルティエリアの外にあり、ボールより1〜2列後ろに味方がいる |

- 4つ目の枠は、ペナルティエリアではシュート、それ以外ではバックパスになる。同時には出ない。
- 各手の行き先はターンの頭にゲームが決める。その手の行き先の候補のうち、攻撃側にいちばん有利なところを選ぶ。
  基準は人数差・前進の大きさ。既存のヒント・CPU の評価を流用する。具体的な基準は設計で決める。
- ショートパス・ロングパスの中で、今のどの手（ショートパス・スルーパス／ロングボール・サイドチェンジ）として扱うかもゲームが決める。
  判定はその手の今の判定に従う。たとえばスルーパスになった場合は、今のスルーパスの判定（読まれたら奪われる）を使う。
- バックパスは判定しない。必ず通る。代償は「前に進めず、1ターンを使う」だけとする。
- シュートの判定は今と同じ。ボールのエリアの人数差で決まり、同数のときは守備に「シュートを読む」を当てられたら阻止される。

### 2. 守備の手（3つ。ペナルティエリアでは4つ）

守備の行き先も、ターンの頭にゲームが決める。

| ボタン | 守備の動き | 行き先 | 読みが当たる相手の手 |
|---|---|---|---|
| ボールに寄せる | プレス | ボールを持つ選手のエリア | ドリブル |
| パスコースを切る | プレス | 相手のショートパスの行き先として予測したエリア | ショートパス |
| 背後を埋める | カバー | 相手のロングパスの行き先として予測したエリア（守備ラインの背後） | ロングパス |
| シュートコースを塞ぐ（ペナルティエリアだけ） | プレス | ボールのエリア | シュート |

- 予測は、攻撃側の行き先を決めるのと同じ決め方で行う。そのため手の種類の読みが当たれば、行き先もほぼ当たる。
- 判定は今の読みの段階（ぴったり・隣・外れ）と人数差の規則を使う。ただし今は「ボールのエリアへの寄せは読みに数えない」。
  これを変えて、「ボールに寄せる」がドリブルを読んだ扱いになるようにする。
- バックパスは守備が読めない手で、守備の選択肢には出さない。

### 3. ポジトラ・ネガトラ（2つずつ）

- ポジトラ: カウンター／保持。カウンターの行き先は選ばない。今の候補（1〜4列前で味方がいるエリア）からゲームが決める。
- ネガトラ: 即時奪回／リトリート（今のまま）。

### 4. 行き先の見せ方

- 自分の手の行き先だけを、選ぶ前に見せる。相手の手の行き先・候補は見せない（同時選択の読み合いを守るため）。
- 手のボタンには、手の名前・行き先のエリア名・判断材料（ヒントが ON のとき、今のヒントの札と同じ人数差など）を載せる。
- 盤面には、自分の各手の行き先への矢印（ボールを運ぶ手）や守る位置を、ボタンと対応づけて描く。ボタンに触れると、対応する表示が強調される。
- エリア名は、その手を選ぶ側から見た名前で書く。
- ボタンの文言は、サッカーで使う言い方で画面詳細設計（`screen-03-match.md`）で決める。手の整理用の表の言葉をそのまま流用しない。

## 受け入れ条件

### 攻撃の手
- [ ] ペナルティエリア外では、攻撃の手のボタンはショートパス・ロングパス・ドリブル・バックパスのうち、条件を満たすものだけが出る（最大4つ）
- [ ] ペナルティエリアでは、バックパスの代わりにシュートが出る。シュートとバックパスが同時に出ることはない
- [ ] 攻撃の手を選ぶと、エリアを選ぶ手順なしで決定できる
- [ ] 各手の行き先は、その手の今の条件で選べるエリアのいずれかになる（ルール上選べない行き先にならない）
- [ ] 同じ局面なら、ゲームが決める行き先は同じになる（決定的）
- [ ] ショートパスの行き先が今のスルーパスの行き先になったときは、今のスルーパスの判定が使われる
- [ ] バックパスは判定なしで通り、ボールは後ろの味方のエリアへ移る
- [ ] 後ろ1〜2列に味方がいないときは、バックパスが出ない

### 守備の手
- [ ] ペナルティエリア外では、守備の手のボタンは「ボールに寄せる」「パスコースを切る」「背後を埋める」の3つ（選べないものは出さない）
- [ ] ペナルティエリアでは、4つ目の「シュートコースを塞ぐ」が出る
- [ ] 「パスコースを切る」を選んだ守備と相手のショートパスが同じエリアなら、読みがぴったり当たった扱いになる（ロングパスと「背後を埋める」も同じ）
- [ ] 「ボールに寄せる」を選び、相手がドリブルしたときは、ドリブルを読んだ扱いで判定される
- [ ] 攻撃がバックパスのときは、守備の手に関わらずボールが後ろへ移る

### ポジトラ・ネガトラ
- [ ] ポジトラはカウンター／保持の2ボタンだけで、カウンターを選ぶとエリアを選ばずに決定できる
- [ ] カウンターの行き先は、今の候補（1〜4列前で味方がいるエリア）のいずれかになる
- [ ] ネガトラは即時奪回／リトリートの2ボタン（今のまま）

### 表示
- [ ] 手のボタンに、手の名前・行き先のエリア名が出る（ヒント ON なら判断材料も出る）
- [ ] 盤面に自分の手の行き先だけが描かれ、相手の手の行き先は描かれない
- [ ] ボタンに触れると、対応する行き先の表示が強調される

### 既存機能との整合
- [ ] CPU は新しい手（攻撃最大4つ、守備3〜4つ、トランジション2つ）から選ぶ
- [ ] チュートリアル・振り返り・理解度チェック・実況など、手の種類を参照する機能が新しい手で動く
- [ ] 中断データ（保存した試合）の読み込みで、旧い手の名前が残っていても壊れない（扱いは設計で決める）
- [ ] 全体テストが3分以内に終わる

## 成功指標

- 1ターンの操作が「ボタンを1つ押して決定」になる（盤面でエリアを選ぶ操作が無くなる）
- 遊んで、読み合いが残っていると感じられること。シャビが遊んで判定し、違和感があれば調整する（特にバックパスの代償、ペナルティエリアの4択）

## スコープ外

以下はこのフェーズでは実装しません:

- 判定の数値・規則そのものの見直し（人数差・読みの規則は今のものを使う）
- 方式（ゾーン／マンツーマン、ポゼッション／カウンター）の変更
- ネガトラの手の変更

## 未決事項

- 行き先を決める「いちばん有利」の具体的な基準（ヒント・CPU の評価のどれを流用するか、同点のときの順）
- ショートパス／ロングパスの中で、今のどの手として扱うかを決める規則（例: スルーパスと普通のショートパスで有利さが同じなら、どちらを優先するか）
- 「背後を埋める」の予測先と、今のカバーの条件（守備側の1列目では選べない等）との関係。条件を満たさないときはボタンを出さないか
- 中断データに旧い手（THROUGH_PASS・LONG_BEHIND・SWITCH など）が残っている場合の扱い（読めるようにするか、中断データを破棄するか）
- チュートリアルの各段階で選べる手の絞り込み（`tutorial.json`）の書き直し方
- ボタンの具体的な文言と見た目（画面詳細設計で決める）
