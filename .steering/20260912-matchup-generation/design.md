# 設計書

## アーキテクチャ概要

マッチアップを「手書きデータ」から「タグ × ルールによる導出」へ置き換える。
**公開APIは変えず**、`matchups.ts` の内部だけを差し替える。

```
formations.ts ──┐
 (positions,    │
  extraTags)    ▼
          formationTags.ts        タグ導出（positions → FormationTag[]）
                 │
                 ▼
          matchupRules.ts         タグ対決ルール表（コンテンツの正本）
                 │
                 ▼
        matchupGenerator.ts       ルール適用 → Matchup 組み立て
                 │
                 ▼
           matchups.ts            export const matchups = buildAllMatchups(formations)
                 │                export function getMatchup(a, b)  ← 既存のまま
                 ▼
   ComparisonPage / MatrixPage / QuizPage / quiz.ts   ← すべて無変更
```

**設計の中心的な制約**: 画面側と既存テストを一切変更しない。
既存テストが無修正で通ることが「壊していない」ことの証明になる。

## コンポーネント設計

### 1. `src/data/formationTags.ts`

**責務**:
- `FormationTag` 型の定義
- `positions` からのタグ導出（`deriveTags`）
- `extraTags` とのマージ（`getTags`）

**実装の要点**:

タグの導出条件は以下とする。**現行4種で検算済み**。

| タグ | 導出条件 | 4-4-2 | 4-3-3 | 4-2-3-1 | 3-5-2 |
|---|---|:-:|:-:|:-:|:-:|
| `3バック` | DF が3人 | | | | ✓ |
| `4バック` | DF が4人 | ✓ | ✓ | ✓ | |
| `1トップ` | FW が1人 | | | ✓ | |
| `2トップ` | FW が2人 | ✓ | | | ✓ |
| `3トップ` | FW が3人 | | ✓ | | |
| `ウイング有` | FW のうち `x<=25 \|\| x>=75` かつ `y>=80` が2人以上 | | ✓ | | |
| `ウイングバック有` | MF のうち `x<=15 \|\| x>=85` かつ `y<=50` が2人以上 | | | | ✓ |
| `守備的MF2枚` | MF のうち `y<=42` が2人 | | | ✓ | |
| `攻撃的MF3枚` | MF のうち `y>=58` が3人以上 | | | ✓ | |
| `中盤3枚` | MF が3人 | | ✓ | | |
| `中盤フラット4枚` | MF が4人 かつ MF の `y` の最大−最小 `<=10` | ✓ | | | |
| `中盤実質5枚` | MF が5人以上 | | | ✓ | ✓ |
| `ライン間が空く` | **導出しない（`extraTags` 専用）** | ✓ | | | |

> ⚠️ `ウイングバック有` の `y<=50` 条件は、4-4-2 のサイドMF（`x=15/85, y=55`）を
> 除外するために必要。幅だけで判定すると 4-4-2 が誤ってウイングバック扱いになる。
>
> ⚠️ `ライン間が空く` は座標から導出しない。FW と MF の y 差で判定しようとすると
> 4-3-3（差35）が 4-4-2（差30）より大きくなり、戦術的な意味と逆転する。
> これが「座標に現れない特徴」の実例であり、`extraTags` を設ける理由。

**`stats` は参照しない。** `stats` はレーダーチャート用の独立した静的値であり、
タグ導出に混ぜると片方の調整がもう片方を静かに壊す（`formations.ts` の既存コメント参照）。

### 2. `src/data/matchupRules.ts`

**責務**: 「自分のタグ × 相手のタグ → 優位ポイントの文 + スコア」の表を持つ。コンテンツの正本。

```ts
export interface MatchupRule {
  id: string;
  /** このルールが語る戦術テーマ。同一テーマからは1件しか発火しない（下記「テーマ」参照） */
  theme: RuleTheme;
  /** 優位を得る側が持つべきタグ（すべて満たす必要がある。空配列なら常に成立） */
  selfTags: readonly FormationTag[];
  /** 相手が持つべきタグ（すべて満たす必要がある） */
  opponentTags: readonly FormationTag[];
  /** 優位ポイントの文。複数の言い回しを持ち、ペアIDのハッシュで決定的に選ぶ */
  advantages: readonly string[];
  /** 総合判定の見出しに差し込む根拠（体言止め） */
  reason: string;
  /** 総合優劣への寄与。原則 1 */
  score: number;
}
```

#### テーマ（重複発火の防止）— レビュー指摘を受けて追加

**1つの噛み合わせで、同一テーマから発火するのは1件だけ**とする
（`applicableRules` が配列順で先に来たものを残し、残りを落とす）。

これが無いと、同じ戦術を別の切り口で書いた複数のルールが同時に当たり、

1. ほぼ同じ文が2行並ぶ
2. 優劣スコアが二重計上される

という二重の事故が起きる。**文字列としては異なるため重複検知をすり抜け、テストは緑のまま
総合判定だけが片側へ静かに歪む。**

事故は2つの経路で起きるため、テーマは両方を塞ぐ:

| 経路 | 内容 | 実例 |
|---|---|---|
| **条件の包含** | あるルールの条件が別のルールの上位集合 | R18 `[ウイングバック有]` ⊂ R19 `[3バック, ウイングバック有]` |
| **タグの共起** | 条件は独立でも、実データ上つねに同じフォーメーションが両方のタグを持つ | 4-4-2 は `中盤フラット4枚` と `ライン間が空く` を常に併せ持つため R07 と R17 が同時発火 |

後者は**ルール単体の定義を見ても分からない**。包含関係の検査だけでは防げないため、
テーマで括るのが確実な手段になる。

テーマ一覧: `中盤の枚数` / `最終ラインの数的関係` / `前線のピン留め` / `レーンの分断` /
`サイドの1対1` / `背後のスペース` / `ウイングバックの押し上げ` / `ウイングバックとの駆け引き` /
`ウイングの封じ込め` / `中盤の陣形維持` / `守備ブロックを広げる` /
`前線と守備的MFの噛み合わせ` / `プレッシング` / `ライン間で受ける` / `速攻`

#### 間引きの副作用 — ルールが「静かに死ぬ」

テーマ間引きは**ルールを黙って落とす**仕組みなので、あるルールが全組み合わせで一度も
採用されない状態を作りうる。実際に初回実装では旧 R17（`攻撃的MF3枚` × `ライン間が空く`）が
常に R07 へ吸収されて死に、**「ライン間」の語が生成文言から丸ごと消えた**。
`soccerTerms.test.ts` は `radarAxes` の説明文で偶然その語を拾えていたため緑のままだった
（＝テーマ導入そのものが、塞ごうとしたのと同型の事故を新たに作っていた）。

対策として2つを置いている:

1. R17 は R07 へ統合し、R07 の**全ての言い回しに「ライン間」を含める**
   （どれが選ばれても用語が残るように）
2. `matchupGenerator.test.ts` に**採用されないルールを検知するテスト**を追加。
   到達不能そのものは誤りとは限らない（フォーメーションが増えれば到達しうる）ため、
   許容リストに明示する方式とし、それ以外が死んだら赤くする。
   現在の許容は `R11` のみ（`3バックかつ中盤フラット4枚` の形を足せば到達する）

**ルールを追加・変更したら、生成後の文言で用語が維持されているかを必ず確認すること。**
ルール表の段階の用語検査（`matchupRules.test.ts`）は、死んだルールの文言でも緑になる。

- 同一ルールの `advantages` 内で文言を重複させない（`matchups.test.ts` が重複を検知する）

### 3. `src/data/matchupGenerator.ts`

**責務**: ルールを適用して `Matchup` を組み立てる。

```ts
export function generateMatchup(a: Formation, b: Formation): Matchup;
export function buildAllMatchups(formations: readonly Formation[]): Matchup[];
```

**総合優劣の算出**:

```
scoreA = Σ(Aに適用されたルールのscore)
scoreB = Σ(Bに適用されたルールのscore)
diff   = scoreA - scoreB

diff >=  2 → "A"
diff <= -2 → "B"
それ以外   → "even"
```

> **`stats` は優劣算出に使わない**（requirements.md の未決事項をここで決定）。
> 理由: タグルールだけで下記の校正アンカーを再現できることを検算済みであり、
> `stats` を混ぜると重み配分の調整が不透明になるうえ、「噛み合わせ」ではなく
> 単純な数値比較に寄ってしまう。`stats` はフォールバック文の生成にのみ使う。

**`overallReason` の組み立て**（A/B相対表現を使わない。フォーメーション名を明示する）:

- 優劣あり: `「{勝者のname}は{勝者側の最上位ルールの根拠}ため、噛み合わせで上回りやすい」`
- 互角: `「{Aの最上位ルールの根拠}と{Bの最上位ルールの根拠}が拮抗しており、優劣がつきにくい」`

「根拠」はルールに `reason` フィールドを持たせるか、`advantages[0]` を短縮した表現を使う。
どちらでもよいが、**生成文がそのまま読める日本語になること**を優先する。

**文言の決定的な選択**:

```ts
// Math.random を使わない。実行のたびに文言が変わるとテストが不安定になる
const index = hash(`${pairId}:${rule.id}`) % rule.advantages.length;
```

`pairId` は `${formationAId}_vs_${formationBId}`（正準順序）。

**フォールバック**: ルールが1件も当たらない側には、`stats` の最大値の軸から
汎用文を生成する（例: `attack` が最大 → 「前線に厚みがあり、攻撃の圧力をかけやすい」）。
`advantagesForA` / `advantagesForB` が**空配列になることは許されない**
（`matchups.test.ts` が検知して落ちる）。

### 4. `src/data/matchups.ts`（既存ファイルの置換）

```ts
export const matchups: Matchup[] = buildAllMatchups(formations);
export function getMatchup(a: string, b: string): Matchup | undefined {
  /* 既存の実装をそのまま維持する */
}
```

`buildAllMatchups` は `formations` の配列順で `i < j` の組を作る。
これにより `formationAId` は常に配列前方となり、既存レコードの正準順序の規約と一致する。
`getMatchup` の入れ替えロジック（`advantagesForA/B` の交換・`overallEdge` の反転・
`overallReason` は据え置き）は**変更しない**。

### 5. `src/types/formation.ts`

`Formation` に `extraTags?: readonly FormationTag[]` を追加する（任意フィールド）。

`FormationTag` 型の定義も **`types/formation.ts` に置く**。当初は「タグ追加時の変更点を
導出ロジックと1箇所にまとめる」ため `formationTags.ts` へ置く方針としたが、
`Formation` がこの型に依存する以上、それでは `types` → `data` の逆流になる。
利用側の利便のため `formationTags.ts` から再公開（`export type { FormationTag }`）する。

## 校正アンカー（最重要）

**ルール表の左右非対称が、全組み合わせの判定を静かに歪める。**
片側のタグにだけルールが厚いと、そのフォーメーションが不当に有利判定される。

歯止めとして、現行4種6組の判定が**手書き時代と一致すること**をテストで固定する。

| 組み合わせ | 手書き時代の `overallEdge` |
|---|---|
| 4-4-2 vs 4-3-3 | `even` |
| 4-4-2 vs 4-2-3-1 | `B`（4-2-3-1 有利） |
| 4-4-2 vs 3-5-2 | `B`（3-5-2 有利） |
| 4-3-3 vs 4-2-3-1 | `even` |
| 4-3-3 vs 3-5-2 | `B`（3-5-2 有利） |
| 4-2-3-1 vs 3-5-2 | `even` |

**検算例**（テーマによる間引き適用後の実出力。確認済み）:

```
4-4-2 vs 4-2-3-1
  A(4-4-2)   : R20, R10                → 2
  B(4-2-3-1) : R08, R03, R04, R07      → 4   ※R17 は R07 と同テーマのため落ちる
  diff = -2 → "B"  ✓

4-4-2 vs 4-3-3
  A(4-4-2) : R15, R16 → 2
  B(4-3-3) : R02, R06 → 2
  diff = 0 → "even" ✓

4-4-2 vs 3-5-2
  A(4-4-2) : R13                → 1   ※R11 は R13 と同テーマのため落ちる
  B(3-5-2) : R08, R01, R18      → 3
  diff = -2 → "B"  ✓
```

全6組の優位ポイント件数（`matchupGenerator.test.ts` が固定している）:

| 組み合わせ | A | B | 判定 |
|---|:-:|:-:|---|
| 4-4-2 vs 4-3-3 | 2 | 2 | `even` |
| 4-4-2 vs 4-2-3-1 | 2 | 4 | `B` |
| 4-4-2 vs 3-5-2 | 1 | 3 | `B` |
| 4-3-3 vs 4-2-3-1 | 2 | 2 | `even` |
| 4-3-3 vs 3-5-2 | 2 | 4 | `B` |
| 4-2-3-1 vs 3-5-2 | 2 | 2 | `even` |

一致しない場合、**閾値をいじるのではなくルール表を補う**こと。
閾値で辻褄を合わせると、フォーメーションを追加したとき（A-2）に破綻する。

## 実装の順序

1. `formationTags.ts` + テスト（土台。ここが間違うと全部ずれる）
2. `matchupRules.ts` + テスト（用語回収テストを先に通す）
3. `matchupGenerator.ts` + テスト（校正アンカーをここで合わせる）
4. `matchups.ts` の置換 → **既存テストが無修正で通ることを確認**
5. 品質チェック（test / typecheck / lint）
6. 目視確認

## セキュリティ考慮事項

- 生成文はすべてアプリ内の静的データ由来であり、外部入力を含まない
- 既存の `TextSegment` による構造化描画（`v-html` を使わない設計）を維持する。
  生成文を導入しても描画経路は変えないため、XSS の新たな経路は生じない
- ハードコードされたURL・シークレット等は本作業で扱わない

## パフォーマンス考慮事項

- `buildAllMatchups` はモジュール読み込み時に1回だけ実行される（`const` への代入）。
  組み合わせ数は n(n-1)/2 で、想定規模（〜10種＝45組）では無視できるコスト
- 画面描画のたびに再生成しないこと（`computed` や関数呼び出しで都度生成しない）

  既存タグで表現できない特徴が出たら、タグとルールを追加する
- **A-3（局面別の形）**: `positions` が保持時／非保持時に分かれた場合、
  `deriveTags` を局面ごとに呼ぶ形へ拡張できる（タグ導出が `positions` の純関数であるため）
- **上書き機構**: 今回は作らない。生成品質の退行が明らかになった場合、
  `matchups.ts` で `overrides` をマージする層を足せば、他を変えずに導入できる
