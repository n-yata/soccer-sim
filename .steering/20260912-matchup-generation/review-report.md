### High（優先対応）

**[バグ] R18 と R19 が包含関係にあり、優位ポイントの重複とスコアの二重計上が起きている**

`src/data/matchupRules.ts`

- R18: `selfTags: ["ウイングバック有"]`, `opponentTags: ["4バック"]`
- R19: `selfTags: ["3バック", "ウイングバック有"]`, `opponentTags: ["4バック"]`

R19 の `selfTags` は R18 の**上位集合**で `opponentTags` は同一。`applicableRules` は
`every` による部分一致フィルタなので、R19 が当たる側は必ず R18 も当たる。
実データで確認した発火状況（手計算、校正アンカー6件の期待値と完全一致するので導出は妥当）:

| 組み合わせ | 3-5-2 側に当たるルール | スコア | diff |
|---|---|---|---|
| 4-4-2 vs 3-5-2 | R08, R01, **R18, R19** | 4 (対 2) | -2 → `B`（閾値ちょうど） |
| 4-3-3 vs 3-5-2 | R05, R09, **R18, R19** | 4 (対 1) | -3 → `B` |
| 4-2-3-1 vs 3-5-2 | **R18, R19**, R10 | 3 (対 2) | -1 → `even` |

実害は2つ。

1. **文言の重複**: 3-5-2 の優位ポイントに「ウイングバックが高い位置を取り、ピッチの幅を
   制圧できる」と「ウイングバックの上下動によって、相手のサイドバックの背後で数的優位を
   作りやすい」が並ぶ。文字列が違うので `matchups.test.ts` の重複検知も
   `matchupRules.test.ts` の横断重複検知も**素通りする**（検知しているのは完全一致のみ）。
2. **スコアの二重計上**: 4バック相手のとき 3-5-2 だけが自動的に +2 を得る。現行データでは
   「ウイングバック有」を持つのは 3-5-2（3バック）だけなので、**R18 が単独で発火することは
   一度もない**。実質「R19 の score を 2 にした」のと同じであり、`matchupRules.ts` 冒頭が
   自ら警告している「片側にだけルールが厚い＝左右非対称」そのもの。しかも
   `4-4-2 vs 3-5-2` は diff = -2 とちょうど閾値なので、**この重複が校正アンカーを
   支えている**（片方を消すと `even` に落ちてテストが赤くなる）。

→ 修正方針: R18 か R19 のどちらかを消し、消して足りなくなった分は「逆側から見た別の
噛み合わせ」で埋める（`design.md` の「閾値をいじるのではなくルール表を補う」に従う）。
例として R18 を削除し、代わりに以下を足すと 6件のアンカーはすべて維持される
（4-4-2 vs 3-5-2 = -2 `B`、4-3-3 vs 3-5-2 = -2 `B`、4-2-3-1 vs 3-5-2 = 0 `even`、
4-4-2 vs 4-2-3-1 = -4 `B`、他は不変）:

```ts
{
  // 中盤に人数をかける形が、間延びした相手のライン間を使える関係。
  // R17（攻撃的MF3枚 → ライン間が空く）と同じ相手条件だが、担い手が中盤の枚数である点が異なる
  id: "R21",
  selfTags: ["中盤実質5枚"],
  opponentTags: ["ライン間が空く"],
  advantages: [
    "中盤に人数をかけられるため、間延びした相手のライン間を使いやすい",
    "実質5枚の中盤が相手の中盤と最終ラインのすき間に人を送り込みやすい",
  ],
  reason: "中盤の人数で相手のライン間を使いやすい点",
  score: 1,
},
```

あわせて、包含関係を**機械的に検知する**テストを `matchupRules.test.ts` に足すことを推奨
（これが無い限り同じ事故が再発し、赤くならない）:

```ts
it("あるルールの条件が別のルールの条件を包含していない（二重計上の検知）", () => {
  const isSubset = (a: readonly string[], b: readonly string[]) => a.every((t) => b.includes(t));
  const offenders: string[] = [];
  for (const outer of matchupRules) {
    for (const inner of matchupRules) {
      if (outer.id === inner.id) continue;
      // inner の条件が outer の条件に含まれる＝outer が当たれば inner も必ず当たる
      if (isSubset(inner.selfTags, outer.selfTags) && isSubset(inner.opponentTags, outer.opponentTags)) {
        offenders.push(`${outer.id} は ${inner.id} を包含している`);
      }
    }
  }
  expect(offenders).toEqual([]);
});
```

### Medium（対応推奨）

**[バグ] `matchups.ts` の再生成ガードが、検知したい変化を検知できていない**

`src/data/matchups.ts`

`generatedFrom !== formations` は `formations` の**参照の差し替え**しか見ていない。
`formations` は `export const` であり ESM の live binding が再代入されることはないため、
この条件は初回以降**永久に false** になる。つまり `currentMatchups()` は事実上
「モジュール読み込み時1回きり」であり、コメントが「防いだ」と主張しているケースは
実際には起こらない。

一方で実際に起こりうる変化 — `formations: Formation[]`（`readonly` でない）への
**その場での破壊的変更**（`formations.push(...)`）— では参照が変わらないので、
やはり再生成されない。フォーメーション追加が反映されずマトリクスが無言で古いままになる、
という懸念どおりの事象が、このガードでは防げない。

さらに、2経路は消費側が分かれている: `QuizPage.vue` は `matchups`（読み込み時スナップ
ショット）、`ComparisonPage.vue` / `MatrixPage.vue` は `getMatchup`。現状は両者が同一配列を
指すため**食い違いは起きない**が、将来 `formations` を動的にした瞬間に「クイズの正解と
比較画面の判定が食い違う」という静かな不整合になる。

→ 修正方法: 起こらない分岐を残すより、単純化して意図を一致させるのが安全。

```ts
// formations はモジュール読み込み時に確定する静的データ。生成は1回だけ行い、
// getMatchup も export const matchups もこの同一の結果を参照する（2経路が食い違わない）
const generated: Matchup[] = buildAllMatchups(formations);
export const matchups: readonly Matchup[] = generated;
```

`matchups` の型を `readonly Matchup[]` にすると、消費側からの破壊的変更（現状 `matchups` は
内部キャッシュ配列と同一参照なので、`sort()` 一発で `getMatchup` の結果順序まで巻き込まれる）
も型で止まる。`QuizPage.vue` / `quiz.ts` が `matchups` をソート・変更していないかは
併せて確認のこと。

**[運用] `design.md` のルール表と検算例が実装と食い違っている（ドキュメント未更新）**

実装には R18 / R19 / R20 の3件が追加されているが、`design.md` のルール表は R01〜R17 のまま。
検算例も現状と合わない（`4-4-2 vs 4-2-3-1` は「A: R10 → 1」とあるが実際は R10 + R20 で 2）。
ルール表はコンテンツの正本であり、設計書が古いと次にルールを足す人が同じ包含関係の罠を踏む。
上の High を直す際に併せて更新すること。

**[運用] `types` → `data` への依存が設計判断に反している**

`src/types/formation.ts` が `import type { FormationTag } from "@/data/formationTags";` を
追加している。`design.md` は「`FormationTag` 型は `formationTags.ts` に置き、`types` からは
参照しない」と明記しており、実装はこれと逆（`types` が `data` を参照し、`formationTags.ts` は
`types` を参照する相互参照）。`import type` なのでビルド時に消え、循環の実害は無く typecheck も
通るが、レイヤの向きが設計と逆であることは記録するか、`FormationTag` を `types` 側へ移すかの
どちらかを選ぶべき。

**[バグ/コンテンツ] 相関するタグによる「準・重複発火」**

> ・攻撃的MF3枚が相手の横並びの中盤4枚の隙間でボールを受けやすい（R07）

意味がほぼ同じ2文が並び、スコアも二重に乗る。4-2-3-1 の優位点が5件と突出している一因。

→ 包含関係だけでなく、**タグの共起によって同時発火するルール対**も検知対象に含める必要がある。
「ルール単体の定義」ではなく「実際の `formations` を入れたときに何が同時に当たるか」を
見るテストでないと防げない。

### 新たな指摘

#### Medium

**[副作用] テーマ間引きで R17 がデッドルール化し、用語「ライン間」が生成文言から消えた**
