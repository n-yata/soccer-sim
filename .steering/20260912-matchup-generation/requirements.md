# 要求内容

## 概要

フォーメーション2件の組み合わせごとに全文手書きしている優位ポイント・総合判定を、
フォーメーションの**特徴タグ**と**タグ同士の噛み合わせルール**から生成する仕組みへ置き換える。
執筆コストを「組み合わせの数」から「ルールの数」へ移し替える。

## 背景

現在 `src/data/matchups.ts` は、組み合わせごとに `advantagesForA` / `advantagesForB` /
`overallEdge` / `overallReason` を手書きで持っている。組み合わせ数は n(n-1)/2 で増えるため、
フォーメーションを 4種→8種にすると 6組→**28組**の執筆が必要になる。

この執筆コストが、以降のコンテンツ拡張（フォーメーション追加・局面別の形）を塞いでいる。
NFR-03「新しいフォーメーションをデータファイルへの追加のみで表示できる」は、
表示という意味では満たしているが、**解説コンテンツの観点では満たせていない**
（追加しても優位ポイントが空のままになる。`matchups.test.ts` はこれを検知して落ちる）。

### 方針（ユーザー決定事項）

1. **全件を生成に統一する。** 手書きの6組は残さない（上書き機構を作らない）
2. **総合優劣（`overallEdge` / `overallReason`）も自動判定する**
3. **タグは `positions` から自動導出し、座標に現れない特徴だけ手動タグで補う**

### 事前調査で判明した制約

登録済みのサッカー用語18件のうち**9件は、削除対象の手書き文にしか登場しない**
（`サイドバック` `センターバック` `2トップ` `1対1` `数的優位` `マンツーマン` `ピン留め`
`5レーン` `コンパクトな守備ブロック`）。

手書き文を単に削除すると、`soccerTerms.test.ts` の「全件の term が実文言に登場する」が落ち、
FR-11（用語のインライン表示）は注釈対象を、FR-10（用語集）は収録根拠を失う。

したがって本作業の要点は「手書き文を捨てる」ことではなく、
**手書き6組をルール表へ蒸留し、9件の用語をテンプレート語彙として引き継ぐ**ことである。
既存の手書き文は、作るべきルールの仕様書として扱う。

## 実装対象の機能

### 1. 特徴タグの導出（`src/data/formationTags.ts`）

- `positions` の `type` 別人数と `x` / `y` 座標から、フォーメーションの特徴タグを機械的に導出する
  （DF×3 → `3バック`、FW×2 → `2トップ`、高い位置のサイドFW → `ウイング有` 等）
- 座標に現れない特徴は `Formation.extraTags?` で補える
- 導出ロジックは `stats`（レーダーチャート用の静的値）と独立させる

### 2. タグ対決ルール表（`src/data/matchupRules.ts`）

- 「自分のタグ × 相手のタグ → 優位ポイントの文 + 優劣スコア」の表を持つ
- 文言は用語集（`soccerTerms`）の語彙で書き、初心者に平易であること（NFR-02）
- 既存の手書き6組の文言をここへ蒸留し、孤立していた9件の用語を回収する

### 3. マッチアップの生成（`src/data/matchupGenerator.ts`）

- ルールを適用して `Matchup` を組み立てる
- 総合優劣はルールのスコア合計と `stats` の軸対決から算出し、`overallEdge` を決める
- `overallReason` はフォーメーション名を明示して組み立てる（A/B相対表現を使わない）
- 同一ルールの複数の言い回しを、ペアIDをシードにした**決定的**な選択で使い分ける
  （`Math.random` を使わない）

### 4. 既存データの置換（`src/data/matchups.ts`）

- 手書き配列を削除し、`buildAllMatchups(formations)` による生成に置き換える
- `matchups` / `getMatchup()` の**公開APIは変更しない**

## 受け入れ条件

### 特徴タグの導出
- [ ] 全フォーメーションについて、期待するタグが `positions` から導出される
- [ ] 座標の境界値で判定が意図どおりに動く
- [ ] `extraTags` で補ったタグが導出結果にマージされる

### タグ対決ルール表
- [ ] ルール表の `advantage` 全文を連結したとき、`soccerTerms` の**18件すべてが出現する**
- [ ] ルールIDが一意である

### マッチアップの生成
- [ ] 全組み合わせで `advantagesForA` / `advantagesForB` がそれぞれ1件以上生成される
- [ ] `overallReason` に「Aは」「Bの」等のA/B相対表現が混入しない
- [ ] 同じ入力に対して決定的な出力を返す（実行のたびに文言が変わらない）
- [ ] ルールが1件も当たらない組み合わせでも破綻せず、フォールバックの文を返す

### 既存データの置換
- [ ] `matchups` / `getMatchup()` のシグネチャが変わっていない
- [ ] 画面側（`.vue`）に変更がない
- [ ] 既存テストを**1つも書き換えずに**全てパスする
  - `matchups.test.ts`（全組の存在・非空・A/B相対表現・重複・入れ替え semantics）
  - `soccerTerms.test.ts`（全用語が実文言に登場する）
  - `quiz.test.ts` および各ページのテスト
- [ ] `npm test` / `npm run typecheck` / `npm run lint` がすべて成功する

### コンテンツ品質
- [ ] 比較画面の優位ポイントが、手書き時代と比べて明らかな品質退行を起こしていない（目視）
- [ ] FR-11 の用語インライン表示が、生成文の中で機能している（目視）
- [ ] 相性マトリクスの判定が `even` に偏りすぎていない（目視。閾値の妥当性確認）
- [ ] 生成文の戦術的妥当性を `docs/content-review-checklist.md` に沿ってセルフレビューした

## 成功指標

- **定量**: フォーメーションを1種追加したときに必要な手書き作業が、
  「既存全件との組み合わせ分の解説文」から「`extraTags` の付与のみ（0〜数行）」になる
- **定性**: 生成された解説文が、手書きのものと読み比べて遜色ない平易さ・具体性を保っている

## スコープ外

以下はこのフェーズでは実装しません:

- **A-2: フォーメーションの追加**（5-3-2 / 4-1-4-1 / 3-4-3 / 4-4-2ダイヤ）
  — 本作業の成果を検証する次段の作業として分離する
- **A-3: 局面別の形**（保持時 / 非保持時）
  — `Formation.positions` の型変更を伴うため独立した作業とする
- **上書き機構**（手書きで生成結果を個別に差し替える仕組み）
  — 「全件を生成に統一」の決定により作らない
- 画面（`.vue`）の変更 — 公開APIを維持する設計のため発生しない想定

## 未決事項

- **判定閾値（`score` が何点差で `A` / `B` / `even` になるか）** は実装時に決める。
  初期値は ±2 とし、既存4種の判定結果が手書き時代（`even` 2件 / `B` 有利 3件相当）から
  大きく乖離しないことを目安に調整する
- **`stats` の軸対決を優劣スコアにどれだけ寄与させるか**（タグルールとの重み配分）も
  実装時に決める。`stats` を効かせすぎると、噛み合わせではなく単純な数値比較になってしまう

## リスク

**生成文の品質が手書きを下回ると、コンテンツの退行になる。** 上書き機構を持たない決定のため、
個別組み合わせへの救済手段がない。ルール表の文言を丁寧に書くこと、および目視確認での
品質判断が歯止めになる。退行が明らかな場合は、上書き機構の追加を別途検討する。
