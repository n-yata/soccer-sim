## 計画と実績の差分

**計画と異なった点**:
- **drawio の作り方**: drawio MCP は使わず、非圧縮 XML を生成する Python スクリプト（作業用領域。リポジトリ外）で作った。全8ページに同じヘッダー・主ナビを同じスタイル値で描く必要があり、スクリプトの方が確実だったため。表示の確認は、draw.io デスクトップの CLI（`draw.io.exe -x -f png -p N`）で PNG に書き出し、目視で行った。PNG はリポジトリに置いていない（diagrams 規約）。
- **ワイヤーフレームの文言**: 文言は実装（`src/data` の教材タイトル・目的・用語）から読み出して埋め込んだ。マトリクスの判定値は、一時的なテストで `getMatchup` の実データを出力して使った。当初は例示パターンで描いたが、review-implementation で「誤解を招く」と指摘され、実データに改めた。
- **functional-overview.md の補修範囲**: 計画では遷移図だけを直す予定だった。実際には UC-06 の関連画面（比較画面 → 自由配置ボード画面）と、モジュール構成図（画面6〜8と参照データ）にも欠けがあり、これも直した。
- **repository-structure.md**: ルールの追加に加え、ディレクトリツリーとデータ層の説明にも古い記述があった。具体的には、PageHeader の「グラデーション背景」、`learningProgress.ts` を「唯一副作用を持つ」とする記述、学習系・ボード系ファイルの記載漏れ。これらもあわせて直した。

## 学んだこと

**技術的な学び**:
- **XML コメント内の `--` は不正**になる。コメントに CSS 変数名（`--width-wide`）を書いたところ XML が壊れた。生成スクリプトに、コメント文字列の検査（`--` を含めば停止）を入れた。
- draw.io デスクトップの CLI でページを指定して書き出すとき、**`-p` は1始まり**（0 と 1 が同じページになる）。
- 主ナビ6項目を 827px 幅に収めるときは、最長のラベル「フォーメーションを選ぶ」が折り返さない幅（146px）を先に確保すると崩れない。

**プロセス上の改善点**:
- 「ドキュメントの陳腐化」は、ワイヤーフレームだけでなく正本（functional-overview.md）・コンポーネント設計・リポジトリ構造にも連鎖して起きていた。画面を追加するたびに、どのドキュメントを同時に直すかを決めておかないと、1か所の更新漏れが複数文書に波及する。
- 書き写し（主ナビの項目、保存タイミングなど）は、正本の場所を注記しておかないと、片方だけが更新される。

## 次回への改善提案

### kit（spec-kit）への改善提案

今回の乖離は、kit のスキルに「画面を変えたら wireframe を更新する」という規定が無いことから起きた。#8〜#10 の3つの PR が、どれも基本設計を更新しないまま通っている。汎用的な問題なので、次の3点を提案する。

1. **`flow-add-feature` A-ステップ8-2 に、画面変更時の wireframe 更新を明記する**
   - 現状は「基本設計やアーキテクチャに影響を与えるか判断し、影響があれば docs を更新」の一文だけで、画面の追加・ルート追加・ナビ変更が「基本設計への影響」と判断されずに通る。
   - 提案: 「`src/pages`（または相当する画面層）・ルーティング・グローバルナビを変えた場合は、`docs/specs/2_basic-design/` のワイヤーフレーム（drawio）と `screen-design.md`、画面の追加・削除では `functional-overview.md` の画面一覧・遷移図も同じ変更で更新する」を、判断に委ねない必須手順として書く。
2. **`review-implementation`（必要なら `review-pre-commit` の運用観点）に検出観点を追加する**
   - 観点: 「画面層・ルーティング・ナビの差分があるのに、ワイヤーフレーム・画面設計の差分が無い」。
   - 現状はどちらのレビューにもこの観点が無く、プロジェクト固有の規約を書いてもレビュー役がそれを読まなければ素通りする（今回の review-pre-commit でも fail open と指摘された）。
3. **`flow-steering` の design テンプレートに「影響するワイヤーフレーム／画面設計」欄を設ける**
   - 計画段階で、どの画面のワイヤーフレームを直すかを書かせる。そうすれば tasklist に更新タスクが自然に入る。現状の design テンプレートには画面設計への影響を書く欄が無い。

参考までに、`specs-basic-design` ガイドは「画面ごとに `wireframe-[slug].drawio` を作る」としているが、本プロジェクトは1ファイル複数ページを選んだ（理由は repository-structure.md「汎用規約からの差分」）。全画面に共通のヘッダー・ナビを持つ Web アプリでは1ファイルの方が画面間の不一致を見つけやすいので、ガイドで選択肢として認める余地があると考える。
